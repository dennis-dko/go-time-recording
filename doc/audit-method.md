# How an audit is run

The method `CLAUDE.md` points at for audits: the workflow, how a finding, a
decision and a candidate that is neither are told apart, the iteration limits,
and the prompts that start each kind of audit. It lives here rather than in
`CLAUDE.md` because that file is loaded into every session and this is needed in
an audit only - moved on 2026-10-09, it took about eleven thousand tokens off
every session that was not one.

Read it whole when an audit starts. Everything `CLAUDE.md` says still holds
during one; where this refers to a section, it is `CLAUDE.md`'s. The record the
logic read keeps is [`audit-ledger.md`](audit-ledger.md), and what waits on the
maintainer is [`audit-open.md`](audit-open.md).

## The workflow

* **Agentic Auditing Workflow:** Start every audit with a new `AUDIT_REPORT.md` - the last one deleted, not added to - and document findings in it sequentially. It is git-ignored and lives for one audit, so what has to outlive the audit goes into the repository in the commit that produces it: a read's row in `doc/audit-ledger.md`, a decision put to the maintainer and a measurement reading cannot make in `doc/audit-open.md`, the reasons in the commit message. Kept for good, the report had grown to 294 KB in three weeks and held the only copy of thirty-odd open decisions.
  1. **Automated first:** Run `golangci-lint run --build-tags "browser integration firefox" ./...`, `go test -race ./...`, `go mod tidy` and `govulncheck ./...`, plus the repository's own checks from CLAUDE.md's Section 3 (`deadcode`, the compose config sweep, `go test ./internal/interface/web/`). Document hard facts.
  2. **Conformance sweep — check the tree against every rule *CLAUDE.md* states mechanically, and put the result in the report as a table.** This is not a re-run of the linter: these are CLAUDE.md's rules, and nothing enforces them. Sweep for a `panic()` outside the one permitted; a SQL statement built by concatenation or `Sprintf`; `path/filepath` on an embed, URL or route path; an inline style or inline `script` in the markup; a user-facing string that does not go through `t('...')` or `data-i18n`; a package-level `var` that is mutable after startup; a `time.Sleep` on a path a request is waiting on; a stuttering `pkg.PkgThing`; a state reported with a toast instead of a banner; a project id read, totalled or changed without passing `RequireVisible`; a stored date built with anything but `model.CalendarDay`. Every hit is read before it is called a violation — the sweep produces candidates, and most of them are not:
     * `internal/interface/web/web.go:82` is the one permitted panic (the embedded assets are missing, so the binary was built wrongly).
     * `internal/infrastructure/persistence/migrations/migrations.go:1334` builds SQL with `Sprintf` and is safe: the only interpolated value is the compile-time constant `model.RoleUser`, and the comment above it says why the constant rather than a literal. **It is one of three, and `test/sqlformat_test.go` names all of them:** `addSessionsAndPreferences` in the same file formats the literal `reports:read` and the constant `model.RoleAdmin`, and `makeSQLiteWait` in `cmd/main.go` formats the busy timeout into a PRAGMA, which takes no parameters at all. This bullet called the first one the only one for as long as the other two had existed, and a line-at-a-time grep agrees with it, because the second one's format string runs over two lines - which is why the test parses the files and fails on a fourth.
     * `announce.Announcement`, `rest.Restart`, `rest.RestartHandler` and `rest.RestartResponse` are name-prefix accidents, not stutters.
     * Three places call `Project.VisibleTo` directly instead of `RequireVisible`, and all three are right: `project_application_service.go:147` *filters* a list rather than refusing a request (and carries the `ViewerID != 0` guard itself), `workbook_application_service.go:306` has to answer with a row-level refusal rather than an `apperror` and deliberately reuses the "no such project" wording so existence is not revealed, and `timesheet_application_service.go:277` cannot reach the zero case at all because `requireUserAndProject` looks the account up first and a booking always belongs to a real one.
     * **Eight hygiene sweeps belong to the same step, and they are named separately because each one has a known answer to compare against.** A sweep whose expected result is written down is one whose *changed* result is the finding; a sweep with no expected result produces a list somebody reads once and never again. Counts below are what each returned when it was written:
       * **Context** — `context.Background()` outside start-up wiring and shutdown timeouts, `context.TODO()` anywhere, and a `context.Context` that is not the first parameter or is not called `ctx`. Ten, none and none. Nine are in `cmd/main.go` and one in the installer's own shutdown, which is where CLAUDE.md's Section 5 permits them - start-up wiring, the context a stop cancels for a scheduled directory run among it, and the shutdown timeouts of the HTTPS front end, of the wait for requests under way and of the installer. One of the eight runs later than start-up: the SQLite connection hook, whose signature carries no context to pass on and whose one statement sets a pragma, which does not wait. The sentence said seven for a while after the port pre-flight made it eight, which is the drift an expected count is there to show.
       * **Logging** — `fmt.Print`, the standard library's `log`, and a write straight to `os.Stderr`, plus `console.*` in the assets. Six in Go, all in `cmd/main.go` and all where no logger can take the line: what `--version` prints, the sentence a rolled-back binary prints and the error when the rollback failed, `die` (which undoes the capture first, because the process is going), the one line saying the log could not be captured, and the reason a migration failed, written past the capture because GoFr's Fatal ends the process straight after it. Those are a command's output, or the last word of a process with no logger, rather than logging, and telling the two apart is the whole of what this sweep is for. One `console.warn` in `app.js`, in `loadOperational`, is a diagnostic for a field the markup has lost, and the comment above it says why it must not throw.
       * **Error handling** — an `fmt.Errorf` carrying an error without `%w`, and a dropped `_ =`. None of the first, and `test/errorwrap_test.go` holds that now: this line said none while one sat in `selfupdate`, because its format string ran over two lines and a grep reads one at a time - the same blind spot as the `Sprintf` above, and the same remedy, a parse. Of the second, all but a handful are `Close` inside a `defer`; the rest are deliberately best-effort and say so in a comment above the line, which is the standard to hold them to, because a dropped error with no sentence beside it cannot be told from a forgotten one.
       * **Orphaned translations** — already three tests rather than a grep, so the sweep is `go test ./internal/interface/web/`: `TestNoTranslationIsUnused` for the orphans and the two coverage cases for the gaps in the other direction.
       * **Orphaned constants, variables and methods** — for constants and variables this is a test rather than a sweep, `test/orphans_test.go`, because the question has one mechanical answer: a package-level value under `internal/` or `cmd/` whose name appears nowhere else in any Go file, the tagged suites and the tests included, fails unless a row says why it is kept — and a row that has stopped being needed fails too. Methods stay a sweep, the same parse widened to every declaration, because there it over-reports by construction: an interface implementation is a use nobody spells, so `MarshalJSON`, `UnmarshalJSON`, both `Unwrap`s and the four `webAuthnUser` methods come back every time and are none of them findings.
       * **Comments that restate the line beneath them** — every word of the comment already present in the next line, which is the one shape of a redundant comment a program can recognise. The rule in this section is far wider than that scan, and the rest of it is only readable.
       * **The same reason written twice** — normalise every comment block by dropping its leading identifier and collapsing the whitespace, then look for two that come out identical. This is the mechanical half of saying a thing once, at the narrowest place that owns it: a rule written out in two files is one explanation and one copy, they drift apart, and the copy is what somebody reads. **Two today**, measured over `internal/` and `cmd/` at 120 characters and up, and both are the benign shape: the sentence about what a success is called, shared by the datasource and the directory connection tests, and the reader's-zone note on two sibling handlers in the same file. So two is the expected result and a *third* is the finding.
       * **What the comments say the framework cannot do** — a workaround carries its reason in a comment, and the reason is a fact about GoFr at the version it was written against; when the requirement moves, the fact can stop being true while the sentence stays. Join each run of comment lines, split it into sentences, and keep those that name GoFr or "the framework" beside a word of limitation - cannot, never, only, no way, without, refuses. **About forty today, in `internal/` and `cmd/`, and every one holds against v1.61.0**, so the finding is one that no longer does, and the moment to run it is a bump of that requirement. `test/frameworkclaims_test.go` makes that moment one nobody can miss: it fails once `go.mod` requires another GoFr than the version it records, until the sweep has been run and the version moved. Sentences, not lines: the first version of this scan was a line-at-a-time grep, and it missed both sentences it had been derived from, because one runs over a line break and the other begins a sentence. Rewritten and proven against those two, it found the same reason in two more files: that the log level is applied by the sink because GoFr's `ChangeLevel` is a data race, three weeks after v1.60.0 had made that field atomic. A reason that has stopped being true is worse than none, because it is the one sentence standing between a reader and the obvious simplification.
     * **The parenthesised `const` block is this tree's recurring blind spot, and it has now hidden two different things.** It hid doc comments that had drifted onto the wrong declaration from `ST1020` and its siblings, because the group's own comment satisfies them; and it hides a dead constant from `unused`, because staticcheck treats a const group as one unit. Measured rather than inferred, by three probes: an ungrouped unused `const`, `var`, `func` and `type` are all four reported, a `var` inside a group whose sibling is used is still reported — and a `const` inside such a group is not. That is why `defaultAutoCloseAfterDays` sat in `internal/infrastructure/config` unread by anything, in a package `golangci-lint` called `0 issues`. When something turns out to be invisible here, ask whether it was in a `const` group before assuming the check is at fault.
  3. **Manual Deep Dive:** Actively read files and search for:
     * *Architecture:* run the dependency-direction grep from CLAUDE.md's Section 5 and report the count, rather than reading three services and forming an impression. Zero is the current state, so a hit is a regression.
     * *Business logic:* work through **What the domain guarantees** in CLAUDE.md's Section 5, rule by rule, and say for each one where it is enforced and what would happen if a caller skipped it. This is the step that is easiest to skip and hardest to fake: layering and error wrapping can both be clean while a report totals somebody else's hours.
     * *Errors:* Grep for `return err` / `fmt.Errorf` to enforce `apperror` usage and missing DE translations.
     * *State:* Grep for package-level `var` and unprotected maps (race conditions).
     * *Frontend:* Check JS/HTML for inline styles, `script-src` violations, and UI DOM quirks.
     * *Duplicates:* Search for redundant business logic or duplicated UI controls.
  4. **When a fix lands, look for the sibling.** Three of the first six sections read in the `app.js`
     rotation yielded a defect, and all three were one shape: **a rule applied in one place and missing
     in the second place that needed it.** `mutate` wrapped a write and the reload behind it in one
     `try`, while the two other callers of `refreshAll` already told those apart. `onwardView` took the
     remembered screen unchecked, while `startingView` checked the same value against the tabs and said
     in a comment why. `handBackTheScreen` reset every form on the way out, and the stopwatch's controls
     are deliberately not in a form. The same shape produced the handover flake twice over: the shared
     wait was fixed and a copy of it in one case was left behind.
     * **No scan finds these, and that is the point rather than a gap in the tooling.** Both places are
       correct read on their own; only the pair is wrong. A duplicate-block scan does not see it because
       the code is not duplicated - the *reasoning* is, and only once.
     * A fourth followed, and it was found *by asking* rather than by reading on: `formData` drops an emptied box, so a cleared description saved as no change - and the project form had already met that and worked around it for itself. `correctionFrom` is the shared reader now.
     * So the habit is the check: having fixed something, ask what else asks the same question, and
       whether the answer is written down twice. The remedy is usually one shared function - `viewIsOffered`,
       `theApplicationAnswered`, `timesheetScopeOf` - rather than a second correction.
     * **Prefer the remedy that makes the omission impossible over the one that has to be remembered.**
       A second correction fixes today's pair; a shared seam fixes the third call site nobody has
       written yet. `settleReleaseWatch` is the shape: three browser cases each had to settle the
       release check before saying what the banner should show, none of them did, and the one that
       lost the race failed on CI while passing alone. The fix was not three waits but one helper
       the next case will reach for without being told. Where a seam is not available, a list that
       fails on a new entry is the next best thing - `TestEveryDecoderOfCompressedInputIsBounded`
       and `TestEveryTableReferencingAnAccountIsPurgedWithIt` are both that, and both exist because
       the remembered version had already been forgotten once.
  5. **Logic read — one file per audit, on a rotation, recorded in `doc/audit-ledger.md`.** Everything above is pattern matching, and a pattern cannot see a ticker that outlives what it reports on, an unbounded retry, a `ctx` that stops being checked halfway down a loop, or a write recorded as applied before the database took it. Only reading does.
     * **The ledger, and why a file is on it.** A file earns a slot when reading is the *only* way to check it: it is long enough that reading is an investment, and what can go wrong in it is invisible to the linter, the race detector and the repository's own checks. That second half is what keeps the list short — `sqldb/purge.go` is the most irreversible code here and is **not** on the ledger, because it is 78 lines with `TestEveryTableReferencingAnAccountIsPurgedWithIt` behind it, which is exactly the case a scan handles. Size alone earns nothing either; `memory.go` is 715 lines of in-memory repositories that a failing test would catch immediately.
     * **The ledger itself is `doc/audit-ledger.md`, and it is kept out of CLAUDE.md on purpose.** It holds the files, what only reading catches in each, every read put to them with its commit, its date, its question and its verdict, and how far `app.js`'s own rotation has got. That record changes with every read and had grown to more than a third of CLAUDE.md, which is loaded into every session and every agent for a history only a logic read needs. It is read when a logic read is about to choose its file; the rules for reading stay here.
     * **The record of a read lives in `doc/audit-ledger.md`, committed beside this file, and that is what its fourth column is for.** `AUDIT_REPORT.md` is a git-ignored scratchpad, so a position recorded only there is gone at the next clone and the next audit opens at the first file again — which is the exact failure the rotation exists to prevent. Each row carries the commit its file was read at, which is the baseline the next walk compares against. The ledger was introduced in one commit as a list of candidates with no read behind any of them, which is why its rows first recorded only the commit each file stood at; every row has been read once since, the first pass over the whole ledger, on 2026-09-26 and 2026-09-27. Moving the row on is part of the read and belongs in the same commit as the fix.
     * **A read is a question put to a file, not a pass over its text, and the finding comes from the question.** The same file answers differently on different days with the same reader — which is why the column records the question and not only the date. So decide the question before opening the file and write it down. A row saying only "read, one finding" cannot tell the next reader which angle is already spent, and the next read then re-asks the last one and reports a clean verdict that means nothing.
     * **A file is in good order when two consecutive reads, asking *different* questions, both come back empty** — not when one does. One clean verdict establishes that one question was answered, which is a smaller claim than it looks. **A finding resets that file to zero**, because the bar asks for two consecutive empty reads, and that property is what keeps the measure honest: it cannot be raised by reading carelessly, only by reading a file that genuinely has nothing left to give against a question nobody asked before. **It is a floor under a file, never a lens the file has outgrown** — nothing leaves the rotation for having met it, and nothing is exempt from the derived scans for having met it.
     * **A read is empty when its question found nothing, wherever what it found turned out to sit.** The question is put to the file, and the answer is as often in what the file drives. A read of `restart_handler.go` that asked whether the next start reads what the card says it will found the fault in the restart package, which handed on the wrong environment - and it was the card's promise that had not been kept. That resets the row, as a finding put to the maintainer does. What leaves it alone is by-catch: something met on the way that is no answer to the question, like a manual still quoting a line the card no longer writes. The other reading - only a fault inside the file counts - would have put that file at the bar on the day its button was found not to read the configuration.
     * **Every audit walks the whole ledger before it reads one of it, and a walk is not ten reads.** Without this the order serves the list rather than the risk, since "a file that changed moves to the front" is aspirational while nothing checks it. For each row, ask what has landed since the commit it records: `git log --oneline <the commit in the row>..HEAD -- <path>`.
       * **The row records a commit and not a date, and that is a decision with a measurement behind it.** A date cannot be ordered against a change made the same day, which is the normal case here rather than the exotic one — a read and the fix it produces land together. Worse, the obvious date form drops those changes without saying so: `git log --since=2026-09-20` returned **0** commits for a file that had **2** that day, because git's approxidate fills a date carrying no time from the *current* time when the date is today, and that measurement was taken at 21:59 on the day in question. `--since="2026-09-20 00:00"` returns both. A commit range has none of this — it is exact, it needs no quoting, and it says which state was read rather than which day somebody read it.
       * **A commit that is the read's own finding does not count**, since it lands after the read by construction and is not evidence that the file moved. Recording the commit rather than the date is also what makes that distinguishable at all: with a date, a fix committed hours after the read looks exactly like an independent change.
       * **The walk re-ranks and does not judge.** A changed file is a candidate for the front of the list, never a finding. With every row read once, the walk has something to order by, and the risk column breaks ties. The commit each row carries is the state it stands at now, so a walk can run before any read has happened.
     * **`app.js` has a rotation of its own** and is read by section rather than as a file; see below.
     * **Adding to the ledger is a decision with a reason, not a reflex.** A new file goes on it when something in it went wrong in a way no check could have caught - which is the same evidence that would otherwise produce a new check. Prefer the check; the ledger is for what a check cannot express.
     * **`app.js` has a rotation of its own, because it cannot be read in one sitting.** Thirteen thousand lines, and CLAUDE.md forbids reading it whole — so it is read by section, in risk order, one or two per audit, and the report names which. The sections are the `// ---` banners the file already carries. Risk order, highest first: `transport` (every request: CSRF, the session ending, the permission revision), `mutations` (every write), `bootstrap` (start-up ordering), `sign-in`, `announcements` (the event stream client), `live log`, then the feature areas. **Where the reading has got to** is recorded beside the files, in `doc/audit-ledger.md`.

  **The shapes that keep coming back**, which are worth more than the record of what was read, because each one predicted the next find:

  * *A rule applied in one place and missing in the second that needs it.* The commonest by far, and the reason for audit step 4.
  * *State that outlives the session that made it.* Found by listing every module-level `let` and asking; it produced a stopwatch still painting one person's time, an entry tally, a calendar month, a sealed page, an unfinished second factor and - worst - a token's value left for whoever sat down next. Outside the forms it hid longer: the import cards and the evaluations, which the redraw registry then drew back; a draw is forgotten at sign-out now unless it is declared the installation's. `class="secret"` is now checked as a class.
  * *A comment stating an intention the code keeps halfway.* No scan sees this: comparing a promise with its keeping is what reading is for.
  * *A bound reasoned about correctly and about the wrong dimension.* The chart picture: right about width, silent about height.
  * *A label written over an element that still declares another key.* Seven sites, now `swapTheLabel`, now checked.
  * *An answer drawn because it arrived rather than because it is the newest.* The calendar and the list of entries, both reached by pressing faster than the server answers; an overtaken load drops its answer now.
  * *A redraw that undoes what was just done.* The wizard's sentence hidden by the step it redrew, the sign-out's language pass drawing the last account's rows back into the tables it had emptied, the account screen's reload closing an enrolment under way. Ask of every redraw what it writes over.

  Six pattern lenses have been run over the whole file and came back clean (block-hash duplication, unreferenced declarations, HTML injection sinks, `await` in a loop, listener accumulation, the `beingEdited` invariant); what they cannot see is wrong logic, which is the whole reason for reading.
     * **One per audit, in rotation, and the ledger names which one was read, against what, and which comes next** — otherwise every audit re-reads the first file and the tenth is never read at all. "Read the ledger" is not a plan; it is how a skim gets reported as a read. Ten files at one an audit is ten audits, which is the honest cost of this step and the reason it is one file rather than a sweep.
     * **Read against the invariants CLAUDE.md already states, not "carefully":** the domain rules in CLAUDE.md's Section 5 first, then `context.Context` first and respected; every ticker and goroutine tied to a lifetime that ends; every error wrapped with `%w` and mapped to an `apperror` code that has a German sentence; a partial update able to say "leave it alone", "set it to this" *and* "clear it"; a state reported with a banner and news with a toast.
     * **It ends in one of two artifacts, never silence:** a failing test and a fix, or a line in the report naming the file, the invariants checked and the verdict. "No finding" is a claim that has to be written down to be worth anything.
     * **Say what reading cannot settle.** Timing against a real browser, a real directory and a real registry is much of what these three do; a read can show that a bound exists, not that it is the right bound. Those go on the acceptance list in `doc/audit-open.md`, to be measured under `task test:browser` / `task test:ldap` rather than being changed on a guess.
     * **Finish by turning each finding into a scan, and run it over the whole tree.** A real finding almost always has a greppable shape, and the scan is what makes "checked the whole project" true rather than a claim. Read one file properly, then let the scan derived from it cover the rest — that is the only version of "check everything" that is not a lie.
  6. **Fix and keep going:** a finding in the report is fixed with a failing test first, committed, merged on a green CI run, and the audit moves on. An audit that halts after every fix spends the session on questions whose answer was always "yes, fix it", and this file already says a finding is not something to put up for a vote. Stop only for the three stops named under *Iterative Audit Limits*. **The analysis-only trigger is the one exception** — it fixes nothing by construction, so it ends by summarising the report and asking which file or issue to fix first.
* **A finding is fixed; a decision is asked about; a candidate that is neither is written down and dropped.** Three outcomes, and mixing them up is expensive in both directions - fixing somebody's deliberate choice unasked, or asking permission to close a hole.

  **It is a finding when somebody can be wrong because of it.** Seven shapes, each drawn from something this repository actually had:
  * *It can hand somebody another person's data or credentials* - a token's value left in the document after a sign-out, an unfinished second factor, project names in a dropdown, a count of the last account's entries.
  * *The screen disagrees with what pressing it will do* - a button reading "Book" on a form still holding an entry, a heading saying "create" while correcting, a label saying "Pause" on a paused viewer.
  * *The application says something untrue about itself* - a "currently in force" line frozen on a process that has restarted, a metrics address that has moved, a drawing announced as "image" and nothing else.
  * *Work is lost, or refused when it should succeed* - a cleared description saved as no change, a year of days refused because the picture was three times the bound.
  * *Something outlives the thing it belonged to* - a stopwatch still painting one person's time onto a handed-back screen, a sealed page after the session under it ended, an overlay over the sign-in form.
  * *A test passes on a state the wiring cannot produce* - a case that cannot fail is a green light held over a path nobody is checking, and from the outside it is indistinguishable from coverage. This repository has had one: the browser case that "passed" against unfixed code because the test cache replayed the previous result. The scenario has to be able to tell the fix from the fault, and only damaging the code under it says which kind you have.
  * *A published security advisory in a dependency*, whether or not `govulncheck` calls it reachable.

  **It is a decision when the code is right and the taste is arguable** - spacing, wording that is already correct in both languages, a bound that is defensible but not what you would pick, a name you would have chosen differently, a test that could be stricter while its current assertion is honest. **Collect these and ask once**, at the end of the section rather than one at a time, and record what was left undone in `doc/audit-open.md`, where it stays until it is decided. Do not fix them unasked: a repository where an agent quietly restyles what it passes is one nobody can review.
  * The line moves for a comment. A stale comment *in code you are already changing* is part of that change and needs no asking - the rule is that the comment is part of the change. A stale comment on its own is a decision, **unless it invites undoing a deliberate one**, and then it is a finding: `screenColours` claimed the document carries the screen's theme, which the server had stopped doing on purpose, and the obvious way to honour that comment was to reintroduce the bug.
  * Accessibility is a finding, not a decision, when it is the difference between being told something and being told nothing: three charts carrying `role="img"` had no name, so the one element on those screens that is entirely picture was announced as "image".
  * **When it is not clear which it is, it is a finding.** The doubt is itself the answer: it means one of the questions above is unsettled, and the two mistakes do not cost the same. Fixing something that turns out to have been harmless costs a diff somebody reads; leaving something that turns out to have mattered costs whoever is using the application, and they will not be filing it as a finding.
  * **A "cleanup" that would make the code worse is none of the three, and is not offered at all — it is refused with the reason.** Listing it, reading it and rejecting it is the deliverable; the edit is not. Consolidation is where this bites, because a shared helper is the right answer often enough that it stops being examined: the three deliberate `VisibleTo` calls named in the conformance sweep look exactly like a rule applied inconsistently, and routing them through `RequireVisible` would break two of them - one filters a list rather than refusing a request, another must answer with wording that does not reveal whether the project exists.

  **It is neither when it looks wrong and is not**, and those go in the report with the reason rather than into a question. The scans produce more of these than of findings, measured: four of five half-filled sentences, five of six confirmations, nine of eleven redraw keys and twenty-six of thirty module variables were candidates that read correctly. Named ones worth remembering: the one-time code travelling as a query parameter (a DELETE body is not reliably forwarded by proxies, and the handler says so), `loadTokens` having no permission guard (the route requires only a session), the zone picker keeping the last account's choice (its loader refills it for every account before anybody sees it).

* **A scan is a source of candidates, not of findings.** Read the code before calling anything a violation, in both directions. Matching bare identifiers over-reports: four of the five hits a stuttering scan returns here are prefix accidents. And a scan blind to build tags under-reports: `deadcode` without `-tags "integration,browser,firefox"` calls the whole test harness unreachable, which is why the CI step passes all three.
* **Iterative Audit Limits:** When asked to loop until the code is "professional", use hard metrics. `golangci-lint` at 0 warnings and a green race detector are the **floor, never the finish**. **There is no iteration cap.** A session runs until the target state below is reached, pauses only for the three stops named there, and if it can move no further first it says so and names what is left.
  * **The cap used to be three, and what replaced it is a definition rather than nothing.** Three was a guard against grinding, and it was the right guard while there was no way to tell progress from motion — an audit that could not say which way it had moved had to be stopped by counting. The four conditions below are that way, so the count is doing no work any more: a session that meets them is finished whether that took one iteration or six, and a session that does not is not finished at three. What the cap did buy, and what has to be kept without it, is that a session cannot run silently — every iteration still records the lenses it applied and what stayed unread, and every read still moves its ledger row in the commit that lands it, so a session cut short hands the next one an exact position instead of a summary.
  * **The target state is reached when all four of these hold at the same time**, and it is what a session runs to:
    1. **Every ledger row stands at the bar** — two consecutive reads asking different questions, both empty. This is arithmetic over the ledger in `doc/audit-ledger.md`, not a judgement, and the ledger says where it stands.
    2. **`golangci-lint run --build-tags "browser integration firefox" ./...` reports 0 issues.**
    3. **`go test -race ./...` is clean**, and `go test ./internal/interface/web/` with it.
    4. **The five signs below hold.**
  * **Three things stop a session, and only these three.** Everything else — a finding fixed with its failing test, a derived scan, a ledger row moved, a branch merged on a green CI run — is the job rather than a question, and putting a finding up for a vote is the audit handing its own work back.
    * **A decision**, in the sense this file already defines: the code is right and the taste is arguable. Collect them and ask once, at the end.
    * **A fix that buys little.** It is a finding by the seven shapes, and either the path it sits on demonstrably cannot be reached — shown, not argued — or the change costs more than the failure it prevents: a wide diff for a narrow gain, new risk on a path that touches somebody's recorded hours, a seam that exists only for a test. Name it with both sides and ask. This is **not** a way round the doubt rule: when it is unclear whether the path is reachable or whether the failure matters, it is a finding and gets fixed.
    * **A genuinely critical decision**, by which this file means one of four things and not "one that feels big": it changes stored hours or a schema on an argument rather than a measurement; it is irreversible or hard to reverse (a force-push, deleting an unmerged branch, reverting somebody else's commit); it widens the scope past what was asked; or it rests on a claim only a real browser, a real directory or a real registry can settle.
  * **The one exception is the analysis-only trigger**, which fixes nothing by construction: it ends by summarising and asking which file to fix first.
  * **There is still no fixed point, and saying so is part of the report.** Each iteration finds things the last one did not, and usually the code did not change — the lens did. A duplicate only a block-hash scan sees survives any number of audits that never run one. So **"no findings" always means "the scans I ran found nothing", never "nothing is there"**, and an audit that reports the second thing is lying about the first. State which lenses were applied, and name what stayed unread.
  * **There is no "done", and there is still a shape a good state has — naming it is what lets an audit tell progress from motion.** Five signs, each of which this tree can be measured against rather than judged by feel:
    1. **The findings move from behaviour to documentation.** A cycle whose first fix is a permission check and whose last is a wrong sentence in a doc comment is a cycle that ran out of behavioural faults. That is the good outcome, not a weak finish — if a read can only find that a *correct* thing is badly explained, the code under it is in order.
    2. **The ratio of wrong comments to missing ones falls.** A wrong one is worse than an absent one, because the next reader believes it and acts on it: `screenColours` claimed the document carries the screen's theme, and the obvious way to honour that comment was to reintroduce the bug the server had stopped producing on purpose. Good means code and prose are interlocked tightly enough that changing one without the other shows up, which `test/doccomments_test.go` and `test/directives_test.go` already do half mechanically.
    3. **Every non-obvious decision carries the measurement that settled it.** The 408:1 deflate ratio, the 1,250:1 PNG, the median of 138 lines against a p90 of 449. A decision with no number attached is one somebody will undo, because without the number the obvious simplification reads as harmless.
    4. **Green tests have been proven by damage.** The hardest of the five and the easiest to fake, which is why it is written above as a step rather than left as an aspiration.
    5. **The gaps are written down rather than absent.** The acceptance list, the file-length row that says plainly the honest reason is a split nobody has made yet, "no finding" recorded as a claim rather than as silence. A tree that names its holes is in better shape than one that knows of none — and a named gap that gets closed has to stop being quoted as one.
  * **A finding resets that file to zero**, because condition 1 asks for two *consecutive* empty reads. That is the property which keeps the measure honest: it cannot be raised by reading carelessly, only by reading a file that genuinely has nothing left to give against a question nobody has asked before. An audit that reads two ledger files and finds something in both has moved the tree and not the count, and both of those are worth reporting as what they are.
  * **Meeting the bar does not mean a file is finished, and reading it that way is the mistake the bar invites.** Two empty reads mean two questions were answered, not all of them. So the bar is a floor under a file, never a lens it has outgrown: no row leaves the rotation for having met it, and none is exempt from the derived scans. "It feels tidier" remains the verdict this whole section exists to refuse.

## Prompts that start an audit

**STRICT SESSION RULE (CRITICAL):** no sub-agent beyond the narrow, briefed exception CLAUDE.md's token economy allows, and none for an audit read or a decision. Process ONE file or logical step at a time, strictly in the main thread. Flush findings to `AUDIT_REPORT.md` as they are made.

**Run to the finish rather than stopping at every file.** A session works through the findings, commits each one atomically, merges on a green CI run and carries on; it halts only for the three stops *Iterative Audit Limits* names — a decision, a fix that buys little, a genuinely critical decision — and it runs until the target state defined there is reached rather than until an iteration count is used up. Sequential still means sequential: one file or logical step at a time, in this thread, never in parallel.
