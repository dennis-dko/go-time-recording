# CLAUDE.md - Core Directives

**What this is:** `Go-Time-Recording` — project time tracking as **a single self-contained binary**. The REST API and the web interface live in the same executable; the UI assets are embedded with `go:embed`, so starting it needs no asset directory and no migration step. Built on [GoFr](https://gofr.dev), structured after [gogs](https://github.com/gogs/gogs). With no database configured it serves an installer on the same port and waits, because there is nowhere to put an account, a project or an hour until a database exists.

## 1. CI/CD, Git & Branching

* **Strict CI Rule:** No merging to `main` without green CI on the PR. Releases are cut exclusively from `main` after a second CI pass.
* **Flakes:** A red check is a red check. Re-run and merge only when green. Do not chain merge commands.
* **Branching First:** NEVER commit directly to `main`. Always create a descriptively named branch (e.g., `audit/error-handling`, `fix/race-condition`) BEFORE making any code changes.
* **A branch is deleted once it is merged**, locally and on `origin`. `main` is the only branch that outlives a piece of work, so look in `git log` for what the last audit branch was called rather than expecting to find it still there.
* **Atomic Commits:** Commit iteratively. Do not bundle multiple fixes into one massive commit. You MUST create a commit immediately after completing *each logical task* or individual fix.
* **Safe Staging:** Strictly avoid `git add .`. Always run `git status` and `git diff` before staging. Use `git add <specific-file>` to prevent accidental commits of debug outputs or scratchpads like `AUDIT_REPORT.md` (which is git-ignored and stays out of a commit on its own — do not add it back).
* **Commit Messages:** Explain **why**, not *what*.
  * **Subject:** a conventional prefix and one plain sentence (`fix: ...`, `feat: ...`, `docs: ...`, `refactor: ...`). This repository uses those prefixes throughout its history; keep them.
  * **Body:** prose explaining the problem, what had to survive the change, and **what was verified rather than assumed** ("measured on the rendered page rather than guessed at", "the importer never sends one - checked, not assumed"). Not a changelog. A commit that fixes a bug says which test failed against the unfixed code.
  * Keep the `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>` trailer.
* **Line endings are decided by `.gitattributes`, not by anyone's `core.autocrlf`.** Load-bearing here, not cosmetic, and the file says why for each rule:
  * `*.sh`, `*.ldif`, `*.conf`, `*.template`, `Dockerfile*`, `*.yml`/`*.yaml` are pinned to LF because they are read by Linux inside a container, where a stray carriage return is not whitespace — a shell script fails as `bad interpreter: /bin/sh^M`, and an LDIF imports as empty, which looks exactly like a wrong base DN.
  * `*.env` and the two `.env*.example` files are read by GoFr's parser rather than by a shell, so `LOG_LEVEL=INFO` would become `INFO\r`.
  * `*.js`, `*.css`, `*.html`, `*.json`, `*.md` are the embedded web assets, served byte for byte.
  * `.golangci-lint-version` is read by golangci-lint-action, which wants a bare version and nothing else on the line.
* **When a file turns up with the wrong endings, read *both* columns of `git ls-files --eol` before reaching for a fix.** They are different faults with different remedies, and the second one is the dangerous one:
  * **`i/crlf`** — the *index* is wrong, so the committed bytes are wrong. `git add --renormalize .`, in a commit of its own.
  * **`w/crlf` or `w/mixed` while `i/lf`** — the commit is fine and the *working copy* is wrong. `--renormalize` reports nothing to do here, because the index it fixes is already correct. This looks clean and is not: `git status` stays empty (git normalises on compare) while `go:embed` reads the working copy, so a build on this machine bakes in CRLF where the same commit built on the Linux runner bakes in LF. `git checkout -- .` on its own does **not** fix it, which is the trap inside the trap: git compares normalised, sees no difference, and skips the file. Delete the offending file first and check it back out — `rm <file> && git checkout -- <file>` — because an absent file is the only thing that makes git write it again with the current attributes. Confirm with `git ls-files --eol` that nothing is left outside `w/lf`, the two `-text` icons, and the empty `.gitkeep` that has no endings to have.
  * It comes back, and not from anybody's own configuration: `core.autocrlf=true` is set in Git for Windows' **system** config, so it is the default for every repository on the machine and changing it there needs elevation. This repository sets `core.autocrlf=false` locally instead, which is the right scope anyway — `.gitattributes` already decides the endings, so the global switch has nothing left to decide here.
  * **The gap is always the suffix, and it has now caught this file three times.** `*.conf` did not match `slapd.conf.template`, which is why `*.template` was added; then `*.svg` matched nothing at all although the shipped mark is embedded and served byte for byte; then `*.json` did not match `build/versioninfo.json.in`, which `sed` substitutes inside a POSIX shell script. Both are pinned now (`*.svg`, and `*.in` rather than `*.json.in` so the next one is covered before it happens). When you add a file type, ask what reads it and whether some *longer* name ends in it — that is the question the rule for its own type cannot answer.

## 2. Development, Audits & Anti-Hallucination

* **Prove Changes:** Write a failing test against unfixed code -> Fix -> Verify pass. Commit must document this.
* **Reproduce First:** Always reproduce bugs (especially timeouts) to capture actual state before diagnosing.
* **Zero Hallucination Audits:** Never guess or assume implementation details. You MUST use CLI tools (`grep`, `cat`, `rg`, `ls`) to read actual files before reviewing. **Burden of Proof:** Every issue you find MUST include the exact file path and line number. Do not critique code you haven't explicitly read into context.
* **Doc comments are load-bearing here.** This codebase states *why* in the comment above the thing, at length — `internal/infrastructure/announce`, `rest.PermissionRevision`, `rest.EventStream`, `service.PrincipalByID`, `noticePermissionChange` and `mutate` in `app.js`. Read the comment before changing the code: it usually already contains the reason the obvious simplification is wrong, and often the incident that produced the rule. When you change such code, the comment is part of the change.
* **Agentic Auditing Workflow:** Always document findings sequentially in an `AUDIT_REPORT.md` scratchpad.
  1. **Automated first:** Run `golangci-lint run --build-tags "browser integration firefox" ./...`, `go test -race ./...`, `go mod tidy` and `govulncheck ./...`, plus the repository's own checks from Section 3 (`deadcode`, the compose config sweep, `go test ./internal/interface/web/`). Document hard facts.
  2. **Conformance sweep — check the tree against every rule *this file* states mechanically, and put the result in the report as a table.** This is not a re-run of the linter: these are this document's rules, and nothing enforces them. Sweep for a `panic()` outside the one permitted; a SQL statement built by concatenation or `Sprintf`; `path/filepath` on an embed, URL or route path; an inline style or inline `script` in the markup; a user-facing string that does not go through `t('...')` or `data-i18n`; a package-level `var` that is mutable after startup; a `time.Sleep` on a path a request is waiting on; a stuttering `pkg.PkgThing`; a state reported with a toast instead of a banner; a project id read, totalled or changed without passing `RequireVisible`; a stored date built with anything but `model.CalendarDay`. Every hit is read before it is called a violation — the sweep produces candidates, and most of them are not:
     * `internal/interface/web/web.go:85` is the one permitted panic (the embedded assets are missing, so the binary was built wrongly).
     * `internal/infrastructure/persistence/migrations/migrations.go:1337` builds SQL with `Sprintf` and is safe: the only interpolated value is the compile-time constant `model.RoleUser`, and the comment above it says why the constant rather than a literal.
     * `announce.Announcement`, `rest.Restart`, `rest.RestartHandler` and `rest.RestartResponse` are name-prefix accidents, not stutters.
     * Three places call `Project.VisibleTo` directly instead of `RequireVisible`, and all three are right: `project_application_service.go:135` *filters* a list rather than refusing a request (and carries the `ViewerID != 0` guard itself), `workbook_application_service.go:305` has to answer with a row-level refusal rather than an `apperror` and deliberately reuses the "no such project" wording so existence is not revealed, and `timesheet_application_service.go:272` cannot reach the zero case at all because `requireUserAndProject` looks the account up first and a booking always belongs to a real one.
  3. **Manual Deep Dive:** Actively read files and search for:
     - *Architecture:* run the dependency-direction grep from Section 5 and report the count, rather than reading three services and forming an impression. Zero is the current state, so a hit is a regression.
     - *Business logic:* work through **What the domain guarantees** in Section 5, rule by rule, and say for each one where it is enforced and what would happen if a caller skipped it. This is the step that is easiest to skip and hardest to fake: layering and error wrapping can both be clean while a report totals somebody else's hours.
     - *Errors:* Grep for `return err` / `fmt.Errorf` to enforce `apperror` usage and missing DE translations.
     - *State:* Grep for package-level `var` and unprotected maps (race conditions).
     - *Frontend:* Check JS/HTML for inline styles, `script-src` violations, and UI DOM quirks.
     - *Duplicates:* Search for redundant business logic or duplicated UI controls.
  4. **Logic read — one file per audit, on a rotation, recorded in the report.** Everything above is pattern matching, and a pattern cannot see a ticker that outlives what it reports on, an unbounded retry, a `ctx` that stops being checked halfway down a loop, or a write recorded as applied before the database took it. Only reading does. The three files that carry the most of that risk and are least visible to a scan are `internal/interface/api/v1/rest/events.go` (a connection held open for minutes, two tickers and a permission revision), `internal/infrastructure/selfupdate/selfupdate.go` (it downloads, verifies and replaces the running binary) and `internal/application/v1/service/ldapsync_application_service.go` (it deletes accounts and the hours recorded against them).
     * **One per audit, in rotation, and the report names which one was read and which comes next** — otherwise every audit re-reads the first file and the third is never read at all. "Read all three" is not a plan; it is how a skim gets reported as a read.
     * **Read against the invariants this file already states, not "carefully":** the domain rules in Section 5 first, then `context.Context` first and respected; every ticker and goroutine tied to a lifetime that ends; every error wrapped with `%w` and mapped to an `apperror` code that has a German sentence; a partial update able to say "leave it alone", "set it to this" *and* "clear it"; a state reported with a banner and news with a toast.
     * **It ends in one of two artifacts, never silence:** a failing test and a fix, or a line in the report naming the file, the invariants checked and the verdict. "No finding" is a claim that has to be written down to be worth anything.
     * **Say what reading cannot settle.** Timing against a real browser, a real directory and a real registry is much of what these three do; a read can show that a bound exists, not that it is the right bound. Those go on an acceptance list to be measured under `task test:browser` / `task test:ldap` rather than being changed on a guess.
     * **Finish by turning each finding into a scan, and run it over the whole tree.** A real finding almost always has a greppable shape, and the scan is what makes "checked the whole project" true rather than a claim. Read one file properly, then let the scan derived from it cover the rest — that is the only version of "check everything" that is not a lie.
  5. **Stop & Ask:** Once the report is full, summarize findings and ask the user which exact file/issue to fix first using TDD.
* **A scan is a source of candidates, not of findings.** Read the code before calling anything a violation, in both directions. Matching bare identifiers over-reports: four of the five hits a stuttering scan returns here are prefix accidents. And a scan blind to build tags under-reports: `deadcode` without `-tags "integration,browser,firefox"` calls the whole test harness unreachable, which is why the CI step passes all three.
* **Iterative Audit Limits:** When asked to loop until the code is "professional", use hard metrics. Stop automatically ONLY when `golangci-lint` outputs 0 warnings, all tests pass with the race detector, OR after a hard limit of **3 iterations** (to prevent infinite loops).
  * **The cap is there because there is no fixed point, and saying so is part of the report.** Each iteration finds things the last one did not, and usually the code did not change — the lens did. A duplicate only a block-hash scan sees survives any number of audits that never run one. So **"no findings" always means "the scans I ran found nothing", never "nothing is there"**, and an audit that reports the second thing is lying about the first. State which lenses were applied, and name what stayed unread.
* **Idiomatic Go:** Strictly follow [Effective Go](https://go.dev/doc/effective_go) principles for all new code and refactorings. Match the formatting the file you are editing already uses rather than a house style imported from elsewhere; `gofmt` and `goimports` are the arbiters, and rewriting the formatting of untouched code does not belong in a commit about something else.
  * **Avoid Code Stuttering** is the naming rule that does hold here: never repeat the package name in an exported identifier (`rest.Handler`, not `rest.RestHandler`). Measured, `internal` now has **zero**, and `TestNothingStuttersAndTheLayeringHolds` keeps it there. The one violation was `config.ConfigLocation` — unexported to `configLocation` (`internal/infrastructure/config/datasource.go:121`), which is also what GoFr calls it, and it never had a caller outside its own package.
  * **The formatting conventions of other Go projects are not this project's, and they are not to be imported.** Measured on this tree, so that nobody "fixes" it into somebody else's house style: blank lines inside function bodies are ordinary here (8,740 of them across 237 files); single-line `var`/`const` outnumber parenthesised groups (37 to 3, and 77 to 33), so group declarations when they belong together rather than as a rule; a private helper above the last exported function is ordinary (168 places in 42 files); and directory and file names are plural where the thing is plural (`persistence/migrations`, `web/assets`, `cmd/configs`, `apperror/codes.go`). A rule that would flag several thousand existing lines is not a convention, it is a rewrite.
* **`go fix`:** Always run as `go fix -embedlit=false ./...` (prevents rewriting promoted fields).
* **Context & Session Protection:** To prevent session limit crashes:
  1. **No parallel agents:** Do NOT spawn sub-agents, parallel instances or background tasks. Work STRICTLY sequentially in the main thread: one step, one file, write to report, move on.
  2. **Limit CLI output:** NEVER run unbounded `grep` or `cat` on large or multiple files. Always use limits (e.g., `grep -m 20`, `head -n 50`, `sed -n 'a,bp'`) to prevent flooding the context window. `app.js` (12,500 lines), `migrations.go` (1,554) and `index.html` (1,470) are what this is about; never read one whole.
  3. **Frequent state saving:** Flush your findings to `AUDIT_REPORT.md` after EVERY single step in the manual deep dive. Do not hold all findings in memory until the end.
* **The `file.go:N` references in this document are checked by a test.** `TestCLAUDEmdStillPointsAtWhatItSaysItDoes` in `test/directives_test.go` reads every `` `path:line` `` cited here and asserts that the line still carries what the sentence around it claims — the one permitted panic, the one `Sprintf`, the one `time.Sleep`, the three deliberate `VisibleTo` calls. It was added after two of the seven had drifted unnoticed as the files around them grew, which is the failure mode a reference has: an auditor follows it, reads an unremarkable line, and concludes the exception is gone. **A new `file:line` in this document needs its row in that table in the same commit** — the test refuses a citation nothing is watching, and a row for a citation that no longer exists.
* **Living Document:** `CLAUDE.md` reflects the current reality. If you modify the project's folder layout, introduce a new standard test command, or change a core architectural convention during a task, you MUST automatically update the relevant sections (e.g., Layout, Commands) in this `CLAUDE.md` file — in the same commit. A directive here that has stopped being true is worse than no directive.

## 3. Testing & Commands

* **Task runner:** [Task](https://taskfile.dev/) via `Taskfile.yml` at the repo root; `.taskrc.yaml` holds the run settings (`interactive: true`, so a missing enum-constrained variable is prompted for rather than failing). `task --list` shows every task and `task --summary <name>` its rationale — those summaries are the authoritative explanation of why a step exists, so read one before changing that task.
* `task test` (Unit), `task test:integration` (SQLite/PG/MySQL), `task test:browser` (Chrome/chromedp), `task test:firefox` (BiDi), `task test:ldap` (a real directory), `task test:traces`, `task test:all`. `task stage` runs the shipped image against a real database, directory and collector; `task probe` checks a database or directory connection using the application's own drivers.
* **Run the task, not the tool underneath.** They wrap the same `go test`, but they are not interchangeable with it. `task test` depends on `tidy` and sets `GOTMPDIR` under the project directory, because Go writes each test binary to `%TEMP%\go-build` and real-time virus scanning on Windows intermittently locks those files — "Access is denied" on a package that compiles perfectly well. A bare `go test ./...` outside a task is fine for a quick single-package check; use `GOTMPDIR` if it starts failing for no reason.
  * **The suites also carry the parallelism CI runs them at** — `-parallel 4` for the integration suite and `-parallel 2` for the browser one. Without it `go test` uses `GOMAXPROCS`, which is 24 on this machine, and every case starts a real instance of the application and (for the browser suite) a headless Chrome to drive it. Two dozen at once does not fail cleanly: it comes back with a scatter of "the application did not become ready within 1m0s", a different scatter each run, none of it about the change being tested. A local gate that fails at random is one people stop reading — and it is not the gate, because CI measures something else.
* **The suites are separated by build tag, not by directory alone:** `integration` (33 files), `browser` (19) and `firefox` (4). The only build tags under `internal/` are platform ones — `unix` / `!unix` in `infrastructure/restart` — so a scan, a linter run or a test run that only ever sees the host platform is blind to `restart_other.go`, which no suite tag covers either. `infrastructure/selfupdate` was the second such pair until its two files were found to hold the same body; they are one file now. That is the general remedy where a platform split has stopped buying anything, because the split is what let the two copies drift unwatched.
* `golangci-lint run --build-tags "browser integration firefox" ./...` — the tags are not optional. Without them the integration, browser and firefox suites are invisible to the linter, which is roughly fifteen hundred lines that decide whether a release is trustworthy. `.golangci.yml` already sets them for a bare `golangci-lint run`; the version is pinned in `.golangci-lint-version` (v2.13.1) so CI, the release workflow and a local run all mean the same thing, and so a new linter release arrives on a deliberate bump rather than in the middle of a release.
* **Race Detector:** `go test -race ./...` is mandatory, and it does not run on this machine: `CGO_ENABLED=0` with no gcc on the PATH, and the race detector needs cgo. **Fallback, as it actually works here:**
  ```
  MSYS_NO_PATHCONV=1 docker run --rm -v /c/Users/Dennis/Projects/go-time-recording:/app -w /app -e GOFLAGS=-buildvcs=false golang:1.27 go test -race ./...
  ```
  Three details, each of which was found by the command failing without them. `MSYS_NO_PATHCONV=1` stops Git Bash rewriting `-w /app` into a Windows path — without it the daemon is handed `C:/Program Files/Git/app` and refuses, which reads as a Docker problem rather than a shell one. `golang:1.27` rather than `golang:latest`, so the toolchain matches `go.mod`. `GOFLAGS=-buildvcs=false` because the mounted `.git` belongs to another user inside the container. WSL is *not* a fallback here: the Ubuntu image on this machine has no Go installed. Around ten minutes for the whole tree, most of it the service and web packages.
* `go mod tidy` & `govulncheck ./...` (Mandatory dependency checks).
* **This repository's own checks live in `ci.yml` rather than in the Taskfile, and each exists because that class had already gone wrong here.** They belong to an audit's automated pass, not to a list of optional extras:
  * **Unreachable code** — `deadcode -test -tags "integration,browser,firefox" ./...`, and the tolerance is **zero**: there is no baseline to keep. Added after a pass found six, one of which was `OvertimeService.BalanceForAll` computing every user's balance for a team overview this application deliberately does not have. The tag list is what stops it reporting the test harness as dead. Pinned (v0.49.0), unlike govulncheck: what it reports depends on the analysis, so a new release finding something new should arrive on a deliberate bump.
    * **A zero from it does not mean there is no dead code, and this is not a quibble.** `deadcode` uses rapid type analysis: as soon as a type is boxed into an interface anywhere — `json.Marshal`, a `%v`, a `t.Logf` — it must assume a type assertion elsewhere could call any of that type's methods, so it marks **every method on it** reachable. Nearly every model type here is marshalled, so a method on one is effectively invisible to that scan. Measured: three methods with no reference anywhere in the repository, tests included — `Project.BelongsToSomebody`, `Timesheet.Recorded`, `User.EffectiveMaxDaily` — sat behind a clean `deadcode` run. The last mattered: it computed a *different* daily cap from the one the service enforces, so the next caller reaching for "the user's effective maximum" would have found the superseded rule under the obvious name. The lens that finds them is a name search over method declarations, and it over-reports: six of its nine hits were interface implementations (`webauthn.User`, `json.Marshaler`), which have to be read before being called dead.
  * **Deployment compose files** — `docker compose config` over every documented overlay combination, plus a check that `compose.yaml` still *refuses* to start without `DB_PASSWORD`. Nothing in the repository had ever parsed these, so a typo in an overlay was found by whoever was deploying, at the moment they were deploying.
* **`internal/interface/web/` is the third check, and the largest:** 75 cases asserting the *structure* of the interface against the code behind it — every route described in the OpenAPI document and every description a real route, every permission the markup names existing and checked somewhere, every gated element reachable by some seeded role, the form limits being the ones the server enforces, the charts reading the fields the statistics endpoint sends, no inline style, no inline script, no form able to fall back to GET, and no banner offering a way to dismiss it. Run `go test ./internal/interface/web/` after touching anything in the interface, not only after touching a string.
* **Definition of done, before opening a PR:** `golangci-lint run --build-tags "browser integration firefox" ./...`, `go test -race ./...`, `go test ./internal/interface/web/`, a clean `go mod tidy`, and the suite that matches the change (see *Scoping*). CI is the gate, but a check nobody ran locally is one that fails in CI on the day it matters.
* **Scoping:** Run *integration* for handler/service/migration changes. Run *browser* for UI changes.
* **Test style:** plain `testing` — there is no `testify/suite` here and testify is only an indirect dependency. Use the in-memory repositories in `internal/infrastructure/persistence/memory` and the `newFixture` helper in the service package rather than hand-rolling a mock; `test/harness` builds the real binary once per suite and starts an instance per case, which is what `test/integration` (HTTP), `test/browser` (chromedp) and `test/firefox` (BiDi) all drive. A case that measures something visual saves the picture it measured — `test/browser/*.png` is git-ignored.
* **Browser Suite Notes:** Runs parallel and is load-sensitive even at the two-at-a-time the task now pins. Under a full-suite run a case can still fail with `page load error net::ERR_ABORTED` or a download that never lands; re-run the case on its own before believing it — and if it fails alone, it is not load, so read it rather than re-running it. Fix missing waits instead of bumping timeouts, and never turn a real failure into a longer timeout.
* `task clean`: Cleans artifacts and orphaned headless browsers.

## 4. Frontend & Pitfalls

* **Vanilla JS UI:** No build step, `go:embed`, strict CSP (`script-src 'self'`). No inline handlers/styles. Setting a style from script goes through the CSSOM (`el.style.minWidth = ...`), never through a `style` attribute.
* **Every user-facing string goes through `t('English literal')` — the English literal *is* the key.** `TRANSLATIONS.en` is deliberately empty, so a key nobody has translated still renders, in English, rather than falling through to a language the reader may not know. Markup carries its English in the element and names its key with `data-i18n`.
  * A missing translation therefore fails **silently**. After touching any string, run `go test ./internal/interface/web/`: `TestEveryTranslationCoversTheMarkup` and `TestEveryTranslationCoversTheCodeLookups` check that every key has German, `TestNoTranslationIsUnused` that none is orphaned, `TestCodeFallbacksAreEnglish` that the fallback is the source language, and `TestEveryServerErrorCodeIsTranslated` that every code the API can return has a sentence.
  * New API error codes need their German entry in the same edit. The client renders them as ``t(`err.${err.code}`, err.message)``.
  * **One word per concept, and a test says so.** `TestOneWordForAnHour` fails if any German string writes the hour unit as a bare `h` while `unit.hours` says something else, because that is two screens disagreeing about the same unit. Hold any newly agreed term to the same standard.
  * **`/api-docs` is the one page that is not translated, and that is a decision rather than a gap.** Everything on it that carries meaning comes out of `/openapi.json` — route paths, parameter and field names, and the descriptions — all English and none of it translatable from the page. Translating the seven labels around them would leave a German frame around an English page. `api-docs.html` declares `lang="en"` and means it, while `app.js` keeps the application's own `documentElement.lang` in step with the reader's choice. The i18n tests read only `/` and `/app.js`, so nothing would report a half-translated version of that page — which is why the reasoning is written at the top of `api-docs.js` rather than left to be re-derived.
  * **There are exactly two dictionaries, and the second is not a duplicate.** The installer carries its own small table (`TestTheInstallerTranslatesItsOwnRefusals`) because it runs before there is a database, so none of the application — `app.js` included — is loaded. Any *other* second copy of a key is a duplicate; two copies agreeing today is how duplicates start.
* **A state gets a banner; news gets a toast.** A toast fades after a few seconds, which is right for "Saved" and wrong for anything that goes on being true after nobody is looking — a newer release, a restart that is coming, maintenance, rights that have changed. Those are banners in `#standing-notices`, they are not dismissable, and they go down when they stop being true. Do not report a state with a toast.
* **State/Refills:** Background loads/saves must not overwrite a partially filled form or read stale server state. `beingEdited(form)` is what tells a loader to leave a half-filled form alone.
* **Duplication:** Search for existing UI controls (e.g., password reveals) before adding new ones. One question gets one control: the role is changed from the dropdown in the user's row and nowhere else, which is why the account form puts that field away while it is editing.
* **One form, two jobs.** Creating and correcting share a form, told apart by a hidden `id` input — the booking form, the role form, the account form and the project form all work this way. A form in edit mode swaps its title and its submit label and shows its `cancel editing` button; saving calls the form's own reset so the next new record is not written over the one just saved.
* **DOM Quirks:**
  * **SVG `hidden`:** SVGs lack this property. Use the attribute + `display: none`.
  * **`form.id`:** Fails if a child input is named `id`. Always use `getAttribute('id')`.
  * **`<select>`:** Has no default empty option; restoring a form defaults to the first entry unless handled. A hidden control that is still `required` cannot be submitted past and cannot be scrolled to, so the form silently does nothing — clear `required` when you hide a field.
  * **Date fields are two boxes.** `enhanceDateFields` keeps a visible text field in the reader's own convention beside the native `input[type=date]`, which stays the named element. Set one from code with `setDateField`; writing `.value` directly changes the box nobody looks at.

## 5. Backend, Architecture, Domain Rules & Concurrency

* **Layout:** `cmd/` (`main.go` and the `configs/` GoFr reads), `internal/domain/` (`model/`, `repository/` interfaces, `service/` — the domain rules, `visibility.go` among them), `internal/application/v1/` (`service/`, plus `command/`, `query/` and `common/` DTOs), `internal/infrastructure/` (`config`, `persistence/{sqldb,memory,migrations}`, `directory` for LDAP, `announce`, `selfupdate`, `imageupdate`, `restart`, `logsink`, `tlsserver`), `internal/interface/` (`api/v1/rest`, `web`, `installer`, `cli`), `internal/pkg/` (`apperror`, `security`, `document`, `spreadsheet`, `imaging`, `qrcode`, `hosting`), `test/` (`harness`, `integration`, `browser`, `firefox`, `ldap`, `probe`), `deploy/`, `build/`.
* **Clean Architecture, and here it is checkable rather than a matter of taste.** Handlers, services and repositories stay separate, and the dependency direction is one grep: `internal/domain` may import neither `internal/infrastructure` nor `internal/interface`, and `internal/application` may not import `internal/interface`. Outside `_test.go` there are currently **zero** violations of either, so a hit is a regression and not a backlog item - state that number in the audit report rather than a verdict on whether the layering "looks clean". Business logic MUST NOT leak into an HTTP handler: the handler resolves who is calling, parses the request, and hands both to a service.
* **What the domain guarantees, and what a business-logic audit checks against.** These rules *are* the product. They are enforced in `internal/domain`, every one of them was written after the version without it went wrong, and a change that quietly widens one is the most expensive change this repository can take. An audit that only checks layering and error wrapping has not audited the business logic at all.
  * **There are no teams and no view across accounts.** A project belongs to exactly one person (`Project.OwnerID`, and `VisibleTo` is ownership); two people working on the same thing have a project each, with the same name if they like, and nothing adds them together. This is why `OvertimeService.BalanceForAll` was dead code rather than a missing feature - and why a request that would total somebody else's hours is a defect, not an enhancement.
  * **A project the viewer may not see is *not found*, never *refused*.** `service.RequireVisible` answers 404 on purpose: the difference between 403 and 404 is itself the leak. A `viewerID` of zero means authentication is switched off - the local trial case - and sees everything.
  * **Every project id that arrives from a caller passes `RequireVisible` before anything is read, totalled or changed.** The project *record* was hidden long before the hours booked against it were: opening a report was enough to learn what somebody had recorded against their own private category, and how much. Archive, transfer and both report paths each carry the check separately.
  * **Two ids, two questions, and both are needed.** `viewerID` decides whether the project may be seen; `onlyUserID` decides whether other people's hours may be. `GenerateProjectTimeReport` takes both because the version that conflated them totalled every colleague's hours for anybody who could open the project.
  * **Only an `active` project accepts bookings, and only a `completed` one can be archived.** Both refusals are typed codes (`projectClosedForBooking`, `archiveNeedsCompleted`), not messages.
  * **The built-in administrator must keep a role that can still administer** (`PermRoleWrite`), or an installation locks itself out of its own user management.
  * **A stored date is midnight UTC of a calendar day and carries no zone** (`model.CalendarDay`). *Which* day is read in the user's own zone, and for the stopwatch it is the day the clock was **started** - somebody who starts at half past eleven at night and stops after midnight worked that evening. One shape only: the version that kept the zone stored 15 July as midnight in Berlin from the clock and midnight UTC from the form, overtime grouped those as two days, each was measured against a full day's target, and the balance on screen was eight hours short of the truth.
  * **One person, one running clock.** `RunningTimer` is keyed on the user, because two would pose a question with no answer - which one the next stop belongs to. It is deliberately not a `Timesheet` with a zero duration: a clock has no duration, and no calendar day, until it is stopped.
  * **A booking is at least `MinBookableHours` (0.01) and at most the configured daily cap, itself bounded by `HoursPerDay`.** Nothing rounds to a quarter-hour grid - the floor exists only to tell a short booking from a mistyped one. The same floor is published in the OpenAPI document and set on the form, so all three agree about what the API takes; changing one means changing three.
  * **A time entry has no status and no approval path.** There is nobody to approve: everyone keeps their own hours and the built-in administrator runs the installation rather than reviewing other people's work. Do not reintroduce a review step, and do not read its absence as an oversight.
  * **An empty synchronisation schedule means "do not run", and that is the safe default** - a run deletes the accounts the directory no longer holds, together with the hours recorded against them. `ValidSchedule` refuses an expression the scheduler would silently drop, because a mistyped one saves cleanly and then never runs, and a job that never runs looks exactly like a directory that has not changed. `LDAPSyncMaxDeleteRatio` bounds how much one run may remove.
* **Dependency Injection:** Inject all external dependencies (DBs, APIs) via constructors/structs to ensure code remains testable.
* **Context Propagation:** Always pass `context.Context` as the very first parameter to all functions handling business logic, DB queries, and external calls. Respect context cancellations. `context.Background()` appears only in startup wiring and in shutdown timeouts — never on a request path.
* **Goroutine Safety:** Never spawn raw goroutines without managing their lifecycle. The inventory in production code is **eight, and enumerable**: two draining the captured stdout/stderr pipes in `logsink` plus one waiting on them, two in `tlsserver` serving HTTPS and the HTTP redirect, one in the installer serving until an answer arrives, one in `restart_handler.go` waiting out the restart grace so the response reaches the browser first, and one in `main.go` listening for the same signals GoFr handles — a second listener on purpose, so the announcement hub is closed before the server tries to drain a stream that by design never finishes. Each of them ends with something. Do not add one outside that pattern; `golang.org/x/sync/errgroup` is not a dependency here and none of the eight needs one, so reaching for it is a dependency decision rather than a style choice.
* **Never `time.Sleep` where a request is waiting.** There is exactly one in `internal/` and `cmd/` — `restart_handler.go:431`, inside that detached goroutine. Anything on a request path waits on `ctx.Done()` or a ticker instead, so an abort is not invisible for the length of the sleep.
* **Shared state:** every package-level `var` in production code is an interface assertion (`var _ repository.UserRepository = ...`), a sentinel error, or a read-only table built once. Nothing mutable lives there, and that is the only reason it needs no lock. Anything that must change at run time carries its own synchronisation instead — the announcement hub is the example.
* **Database Resource Management:** the pool is **GoFr's, not this code's**. Nothing here holds a `*sql.DB` to tune, and `SetMaxOpenConns` and friends appear nowhere in the tree. Tuning is configuration — `DB_MAX_IDLE_CONNECTION` and `DB_MAX_OPEN_CONNECTION` in `cmd/configs/.env` and `deploy/.env.binary.example`, commented out at GoFr's defaults. Change those with a measured reason; do not reach for the Go API instead.
* **`./configs` is resolved from the process working directory, not from the binary.** That is GoFr's own `configLocation`, mirrored by this package's constant of the same name so `DatabaseConfigured` looks exactly where GoFr will. Launching `./bin/app` from the repository root therefore finds no configuration and leaves `container.SQL` a **typed** nil, which `db == nil` does not catch; `cmd/main.go` fails fast on that rather than serving 500s. `APP_ENV` is likewise read from the environment at start-up, so setting it for a `go build` compiles in nothing and GoFr quietly falls back to `.local.env`. Both are invisible to unit tests and to running the binary from a directory that happens to contain `configs/` — verify with the actual launcher command.
* **Path handling:** `path/filepath` is strictly for real files on disk (`selfupdate`, `imageupdate`, `config`). Embedded-asset paths, URL paths and route prefixes are slash paths and must never touch `filepath` — on Windows it would build `assets\app.js`, which the `embed.FS` does not contain. The slash-only `path` package is currently imported nowhere; `fs.Sub` and `http.FS` handle it.
* **Errors:** API uses closed catalogue (`internal/pkg/apperror`), rendered client-side via `t('err.' + code)`. **Mandatory:** New codes require a German translation in tests. Never silently drop errors; always wrap them (`%w`) for context.
  * **No Panics:** Never use `panic()` for business logic, control flow, or validation errors. Return wrapped errors up the stack. `panic` is reserved for a programmer error that cannot be recovered from, and there is exactly one in production code — `internal/interface/web/web.go:85`, where the embedded assets are missing, which means the binary was built wrongly.
* **Partial updates say three things, not two.** An update DTO of pointers can express "leave it alone" and "set it to this" and nothing else, so a field that has to be *emptiable* needs the third state said out loud — `UpdateProjectCommand.ClearEndDate`, and an end date that arrives present but empty. Never overload nil to mean "clear": the callers that say nothing rely on nil meaning nothing.
* **GoFr:** Config read in `gofr.New()`. Changing metrics/trace/DB configs requires storing state and triggering a restart. Anything needing the raw `http.ResponseWriter` — a connection held open and written to over minutes, like the event stream — is middleware rather than a GoFr handler, because "return a value, return an error" is the wrong shape for it by construction.

## 6. Releases

* **Two ways in, and they mean different things.** A merge to `main` cuts the next **patch**: the version is written down nowhere, the workflow reads the newest tag and counts on, so there is no file to forget to bump and no way for a tag and a constant to disagree. A tag pushed by hand (`task release VERSION=vX.Y.Z`) releases exactly that version, and the next merge counts on from it — that is how a minor or major bump is made.
* **Both paths require a green CI run on `main` for the commit being released, and neither verifies for itself.** A tag *asks* whether CI passed for the commit it points at and refuses if it has not. It used to run a subset of its own instead, which is how v0.2.0 shipped from a commit whose Firefox job was red.
* **Build from a clean tree.** The version comes from git at build time, so a dirty working tree is what the binary reports to whoever installed it.
* **Artifacts:** Builds `linux/amd64`, `linux/arm64` images, and 4 platform binaries. Images are verified on both architectures before publishing.
* **The `.syso` filename is load-bearing.** The Go toolchain links *any* `.syso` in a package directory with no import and no build tag, so `goversioninfo`'s default `resource.syso` would end up in the linux and darwin binaries too — the release builds four platforms in one loop, in one working directory. `build/windows-resource.sh` writes `cmd/resource_windows_amd64.syso` instead, where the suffix confines it exactly as it confines a `.go` file, and removes it again afterwards. `*.syso` is git-ignored for the same reason: a committed one would be linked with whatever version it was written with, for ever.
* **A version Windows cannot parse fails quietly, not loudly.** The resource script strips the `v`, takes the three numbers and zeroes the fourth, and falls back to `0.0.0.0` for a version that is not numeric at all — because an unparsed one simply reads `0.0.0.0` in the Properties dialog and says nothing about why.

## 7. Enterprise SDLC & Production Readiness

* **Zero-Downtime Migrations:** Database schema changes MUST be backward compatible. Use multi-phase deployments (e.g., add column -> dual write -> switch read -> drop column). Never drop or rename columns in a single release.
* **A migration runs against somebody's recorded hours, and it runs on three dialects.** `migrations.go` is the longest file in the repository and the chain is append-only: a migration in the middle of it can be looking at a name a later one renames, which is why the ones that need to say so do. Add to the end, never edit an applied one, and prove it under `task test:integration DB=postgres` and `DB=mysql` as well as SQLite.
  * **A migration is atomic, except on MySQL when it changes both the schema and the data.** GoFr runs each one inside a transaction — `migration.Datasource.SQL` *is* the `*sql.Tx`, so every statement in a migration commits or rolls back together, `giveEveryProjectAnOwner`'s row-at-a-time work included. MySQL commits implicitly on DDL, so a migration that alters a table and then updates rows runs its `UPDATE` outside that transaction: the schema change has landed, the data change fails, and nothing goes back. `rememberWhenASessionWasLastUsed` is what that costs — it adds `last_seen_at` and fills it precisely so an update does not sign everybody out, and split on MySQL it is the thing that signs everybody out. **A new migration needing both is two migrations, schema first.** Six existing ones mix them and are named in `TestNoNewMigrationMixesSchemaAndDataChanges`, which guards the seventh; they are listed rather than fixed because the chain is append-only and they have already run everywhere.
* **Secret Management:** Strictly forbid hardcoded secrets, API keys, or private credentials in code or configs. Use environment variables or secret stores exclusively. `configs/datasource.json` and `deploy/.env` hold real passwords and are git-ignored; the `.example` files beside them are what belongs in the repository. `deploy/.env.ci` is git-ignored too, for a less obvious reason: it holds *invented* passwords, and a file of plausible-looking credentials in a deployment folder is one somebody eventually copies.
* **The payload is personal data, and one function is the erasure path.** Recorded hours are what somebody is paid for, so an account and its record go together. `sqldb.PurgeUser` removes them in one transaction, in foreign-key order: running timers, time entries, privately owned projects, api tokens, passkeys, sessions, then the account. Directory synchronisation calls it, and so does an administrator deleting an account; it is irreversible either way.
  * **A new table with a foreign key to `users` is added to that list in the same commit.** A missing one does not fail loudly: on PostgreSQL and MySQL it makes the final delete impossible, and on SQLite - where foreign keys are not enforced unless asked for - it silently leaves rows pointing at an account that no longer exists. This has already happened once, with passkeys.
  * **`grep 'REFERENCES users(id)'` finds most of them and is not sufficient.** `projects.owner_id` was added by an `ALTER` and appears in no `CREATE TABLE`, so it is invisible to that scan - which is the general lesson: read the migration chain for the column, not only the create statement.
  * **`TestEveryTableReferencingAnAccountIsPurgedWithIt` now checks it**, in `test/purge_test.go`. It reads the whole chain for both shapes, follows `ALTER TABLE … RENAME TO` (the SQLite rebuild creates `timesheets_new` and renames it), and requires a matching `DELETE FROM` in `purge.go`. The rule above is still the rule; this is what notices when somebody does not follow it. Verified by removing each of the six deletions in turn and by adding a table with a foreign key to `users` and no deletion — every one is reported.
  * **It is a transaction and must stay one.** The reasoning that every step is idempotent and a failed purge repeats on the next run does not survive the failure it was meant to cover: the final delete is the one that gets refused, and by then the hours are already gone. Inside a transaction, the account and its hours both survive the error.
* **`deploy/OPERATIONS.md` is the operational contract** - what is being deployed, the four supported shapes (compose, compose with TLS, single binary, bare container), where configuration comes from, and which values are worth setting deliberately. It is written for whoever runs this rather than for whoever builds it, so a change to how the binary is configured, started or shut down belongs in it in the same commit. The README links it; this file is the reminder that it is part of the change.
* **Observability & Logging:** Use structured logging (e.g., standard library `slog` or project logger) with contextual keys (request_id, user_id). Avoid raw `fmt.Println` in production code. GoFr provides two health endpoints and the load-bearing one is **`/.well-known/alive`**, not `/.well-known/health`: `alive` is what the Dockerfile's `HEALTHCHECK` and `deploy/compose.yaml` both probe, so a middleware that turns it away gets the container killed and replaced. Keep both reachable. Two already depend on this and both are correct — `maintenanceExempt` passes anything outside `/api/`, and `KeepThePlainPortLocal` lets them through because both probes dial `127.0.0.1`, which is loopback.
* **API Backward Compatibility:** Do not introduce breaking changes to existing API request/response contracts without a versioning strategy. Payload fields must be treated as immutable once public. A field a browser already reads is part of that contract even when no external client exists.
* **What arrives is not what it becomes: bound the decoded size, not only the bytes.** One audit found this three times in three packages, and it is invisible to the linter, the race detector and every suite — there is nothing wrong with the line, and any test fast enough to keep uses an input small enough to hide it. Measured, not estimated: a 32 MB workbook unpacks to ~13 GB (deflate reaches **408:1** on real sheet XML); a 199 KB logo decodes to **244 MB** (a flat PNG compresses ~1250:1), three times per save; a 260 KB chart costs **782 MB** (a canvas produces RGBA, and splitting the alpha means inflating it all). Read the header first — `image.DecodeConfig`, or the library's own size option — refuse what is too large, and pick the bound from a measurement rather than a guess. `TestEveryDecoderOfCompressedInputIsBounded` lists every call site that decodes compressed input and fails on a new one, so the fourth is caught rather than found.
* **Input validation & injection boundaries** — validate and sanitize at the application boundary, and know which boundary each one is:
  * **SQL:** parameterised queries only, through the repository interfaces. Never build a statement by concatenation or `Sprintf` — Section 2 names the one documented exception and why it is one.
  * **HTML:** the served document is assembled server-side so it can carry the instance's own name and mark, which makes a configured title an injection site — `TestAConfiguredTitleCannotCloseItsOwnTag` is that check. A configured logo is served from an endpoint at a stable address rather than inlined as a `data:` URI, and one that is not an image is refused.
  * **Imports:** a spreadsheet row that fails says which row and why, in German as well as English (`TestEveryImportRowProblemIsTranslated`).
  * **CSRF:** a state-changing request must carry the double-submit token — the `gtr_csrf` cookie echoed back in `X-CSRF-Token` (`rest/csrf.go`). A new mutating route is inside that check, not beside it.
  * **Transport:** HTTPS is terminated in-process when configured (`tlsserver`), and GoFr's plain port then answers only the loopback address the front end dials from.
* **Authorisation is enforced server-side and only *reflected* on screen.** Every request resolves who is calling from the database, so a withdrawn right is refused on the very next call whatever the browser believes. What the interface adds is telling somebody: the revision travels on every response, the open event stream carries a change to a page nobody is touching, and the once-a-minute poll is the fallback under both. Never hide a control instead of enforcing a rule, and never offer one the server would refuse.
* **The installer's token is the sign-in.** Answering the installer proves more than a password does — it is read from the process log, and it decides where the data lives — so the browser that answered it is handed a session rather than being sent to type `changeme123`. Two conditions carry that, and both must survive any change to it: an installation that never served an installer has no token and the claim then has no working path at all (an empty configured token must be refused *before* any comparison, or an absent header matches it), and the claim stops working the moment the built-in administrator's password is changed — the same moment the documented password stops working.
* **Design rationale lives in the code and in the commit, not in an `adr/` directory** — there isn't one, and adding a parallel format would split the record. The convention is a package or declaration doc comment stating why the non-obvious choice was made, plus a commit body recording the alternatives and what was verified. Follow that for structural changes.
