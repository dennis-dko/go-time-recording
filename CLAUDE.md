# CLAUDE.md - Core Directives

**What this is:** `Go-Time-Recording` — project time tracking as **a single self-contained binary**. The REST API and the web interface live in the same executable; the UI assets are embedded with `go:embed`, so starting it needs no asset directory and no migration step. Built on [GoFr](https://gofr.dev), structured after [gogs](https://github.com/gogs/gogs). With no database configured it serves an installer on the same port and waits, because there is nowhere to put an account, a project or an hour until a database exists.

## 1. CI/CD, Git & Branching

* **Strict CI Rule:** No merging to `main` without green CI on the PR. Releases are cut exclusively from `main` after a second CI pass.
* **Flakes:** A red check is a red check. Re-run and merge only when green. Do not chain merge commands.
* **Branching First:** NEVER commit directly to `main`. Always create a descriptively named branch (e.g., `audit/error-handling`, `fix/race-condition`) BEFORE making any code changes.
* **A branch is deleted once it is merged**, locally and on `origin`. `main` is the only branch that outlives a piece of work, so look in `git log` for what the last audit branch was called rather than expecting to find it still there.
* **Atomic Commits:** Commit iteratively. Do not bundle multiple fixes into one massive commit. You MUST create a commit immediately after completing *each logical task* or individual fix.
* **Safe Staging:** Strictly avoid `git add .`. Always run `git status` and `git diff` before staging. Use `git add <specific-file>` to prevent accidental commits of debug outputs or scratchpads like `AUDIT_REPORT.md` (which is git-ignored and stays out of a commit on its own — do not add it back).
* **Everything that reaches GitHub is written in English.** Commit subjects and bodies, branch names, pull request titles and descriptions, issue text, review comments, release notes. The language of the conversation that produced the work does not decide this: the repository is the artefact, it outlives the conversation, and whoever reads it next — a contributor, a security reporter, `git log` in five years — did not have the conversation. A history in two languages is searchable in neither.
  * **The conversation is not an artefact, and it is not covered by this.** Talk to whoever is asking in whatever language they are writing in — that is a conversation, and it ends. The moment the same thought becomes a commit, a comment in the tree, a pull request or an issue, it is English. The rule above is about what outlives the exchange, not about the exchange.
  * **The exception is quotation, and it is narrow.** A German UI string, a translation value or an error sentence may be quoted verbatim, because it is the evidence being discussed rather than the prose discussing it — a commit about `err.logoTooManyPixels` should show what it now says. The sentences around the quote stay English.
  * **This is not mechanically checked, and the obvious check would be wrong in both directions.** Searching for umlauts misses German that has none — `docs: sign-in und den Event-Stream-Client gelesen, ohne Fund` is on `main` and contains not one — and it flags the translation commits, whose bodies quote German on purpose. So this is a rule held by whoever is writing, which is worth saying plainly rather than implying a guard exists.
  * It has been broken: four commits and four pull request titles between `7142e1b` and `5b1d147` are German. They are merged and stay as they are — rewriting `main` costs more than the inconsistency does — so they are the record of why this rule is written down.
* **Commit Messages:** Explain **why**, not *what*.
  * **Subject:** a conventional prefix and one plain sentence (`fix: ...`, `feat: ...`, `docs: ...`, `refactor: ...`). This repository uses those prefixes throughout its history; keep them.
  * **Body:** prose explaining the problem, what had to survive the change, and **what was verified rather than assumed** ("measured on the rendered page rather than guessed at", "the importer never sends one - checked, not assumed"). Not a changelog. A commit that fixes a bug says which test failed against the unfixed code.
  * Keep the `Co-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>` trailer.
* **Line endings are decided by `.gitattributes`, not by anyone's `core.autocrlf`.** Load-bearing here, not cosmetic, and the file says why for each rule:
  * `*.sh`, `*.ldif`, `*.conf`, `*.template`, `Dockerfile*`, `*.yml`/`*.yaml` are pinned to LF because they are read by Linux inside a container, where a stray carriage return is not whitespace — a shell script fails as `bad interpreter: /bin/sh^M`, and an LDIF imports as empty, which looks exactly like a wrong base DN.
  * `*.env` and the two `.env*.example` files are read by GoFr's parser rather than by a shell, so `LOG_LEVEL=INFO` would become `INFO\r`.
  * `*.js`, `*.css`, `*.html`, `*.json`, `*.md` are the embedded web assets, served byte for byte.
  * `.golangci-lint-version` is read by golangci-lint-action, which wants a bare version and nothing else on the line.
* **When a file turns up with the wrong endings, read *both* columns of `git ls-files --eol` before reaching for a fix.** They are different faults with different remedies, and the second one is the dangerous one:
  * **`i/crlf`** — the *index* is wrong, so the committed bytes are wrong. `git add --renormalize .`, in a commit of its own.
  * **`w/crlf` or `w/mixed` while `i/lf`** — the commit is fine and the *working copy* is wrong. `--renormalize` reports nothing to do here, because the index it fixes is already correct. This looks clean and is not: `git status` stays empty (git normalises on compare) while `go:embed` reads the working copy, so a build on this machine bakes in CRLF where the same commit built on the Linux runner bakes in LF. `git checkout -- .` on its own does **not** reliably fix it, which is the trap inside the trap. Whether it works at all turns on something nobody thinks about while repairing endings: while git still reports the file as modified it restores it correctly, but the moment anything refreshes the index stat cache — and `git add --renormalize .`, one bullet above, does exactly that — `git status` goes empty and the same command becomes a silent no-op, because git compares normalised, sees no difference, and skips the file. So the remedy that always works is to delete the offending file first and check it back out — `rm <file> && git checkout -- <file>` — because an absent file is the only thing that makes git write it again with the current attributes. Confirm with `git ls-files --eol` that nothing is left outside `w/lf`, the two `-text` icons, and the empty `.gitkeep` that has no endings to have.
  * It comes back, and not from anybody's own configuration: `core.autocrlf=true` is set in Git for Windows' **system** config, so it is the default for every repository on the machine and changing it there needs elevation. This repository sets `core.autocrlf=false` locally instead, which is the right scope anyway — `.gitattributes` already decides the endings, so the global switch has nothing left to decide here. A local setting is not inherited by a fresh clone, though, so it is the first thing to check rather than the last when `w/crlf` turns up on a machine where it had been dealt with before.
  * **The gap is always the suffix, and it has now caught this file three times.** `*.conf` did not match `slapd.conf.template`, which is why `*.template` was added; then `*.svg` matched nothing at all although the shipped mark is embedded and served byte for byte; then `*.json` did not match `build/versioninfo.json.in`, which `sed` substitutes inside a POSIX shell script. Both are pinned now (`*.svg`, and `*.in` rather than `*.json.in` so the next one is covered before it happens). When you add a file type, ask what reads it and whether some *longer* name ends in it — that is the question the rule for its own type cannot answer.

## 2. Development, Audits & Anti-Hallucination

* **Prove Changes:** Write a failing test against unfixed code -> Fix -> Verify pass. Commit must document this.
  * **Where that order cannot be had, damage the code the test covers and watch it go red** — revert the one line, run it, put it back. A test written after the fix is one nobody has ever seen fail, and this repository has already had one: the browser counter-check that "passed" against unfixed code because Go's test cache replayed the previous result (Section 3 — the giveaway is `ok ... (cached)`, and `-count=1` is the remedy). Nothing about that bar looked wrong.
  * **A damage test that stays green has two possible meanings, and they are opposites: the test is blind, or the damage was not damage.** Settle which before believing either, because only one of them is news about the test. The shapes that produce the second are worth knowing in advance, because none of them is obvious in the moment: a value written at *two* sites, so breaking one leaves the other still satisfying the check; a guard broken in a way that removes the logging rather than the mechanism; a scan re-run after its own fix. Count the occurrences of what you are about to break, and make sure the break removes the mechanism rather than one of its effects.
  * **A break that stops the package compiling measures the compiler, not the mechanism**, and it is the silence that looks most like a result, because the suite does come back red. Deleting an assignment leaves its locals unused, which in Go is a build error: not one test ran. **Read what the red says, not that it is red.** The pre-fix state also has to be one the code could plausibly have been in — moving a statement back above the error check compiles and is a shape somebody would have written; `if cond && false` compiles and is not, which is what separates a proof from a mutation.
* **Reproduce First:** Always reproduce bugs (especially timeouts) to capture actual state before diagnosing.
* **Zero Hallucination Audits:** Never guess or assume implementation details. You MUST use CLI tools (`grep`, `cat`, `rg`, `ls`) to read actual files before reviewing. **Burden of Proof:** Every issue you find MUST include the exact file path and line number. Do not critique code you haven't explicitly read into context.
  * **A no-finding is a claim too, and it is wrong about as often as a finding.** "I looked and there is nothing there" has to be earned by the same reading as "here is what is wrong" - and it is the more comfortable of the two to leave unearned, because nothing comes back to contradict it. A green test and an empty scan are observations, not verdicts; what they establish is that *this* test and *that* scan found nothing. **So prove both rather than reading them:** damage the code a green test covers, as above, and run an empty scan against a case you already know it should catch. An unproven scan and a broken one are the same output — the backtick check further down returned 6 of 13 paths and reported nothing wrong, which is worse than having no check at all, and it looked exactly like a clean sweep.
  * **Reading this repository's own files is only the first half.** The answer is as often somewhere the tree cannot show it, and there are four places worth naming because they are the ones that get skipped: the dependency's own source under `go env GOMODCACHE`, or upstream where the module is published; `git`, for anything about when or why something became the way it is; a throwaway probe written to settle one question and then deleted; and the command this document already names, rather than one improvised on the spot, because an improvised invocation is a second thing to be wrong about. Both have already decided a question here: which DOMException Chromium raises for a certificate error was settled by downloading `authentication_credentials_container.cc` and reading the line, against two summaries that disagreed with each other; and whether a dependency had been missed or had simply been published since was settled by the module proxy's own timestamps.
* **Only the essential is written down, and the test is whether the code could have said it.** A comment earns its place by carrying what the code cannot: why this and not the obvious alternative, what went wrong when it was done the other way, which constraint outside this file decides it, what a caller must not assume. Everything else is deleted rather than improved — a sentence that restates the line beneath it, narrates what is plainly visible, repeats what the name already says, or explains a language feature. The same goes for a name that has to be read past to reach the meaning.
  * **This sharpens the rule below rather than contradicting it, and the two are easy to mistake for opposites.** "State why, at length" is about *content*: the length that earns its place is the length of the reason. `announce`, `rest.EventStream` and `mutate` are long because each carries a decision and the incident behind it, and shortening them would delete the reason. A comment that is long because it is thorough about the obvious is the thing this forbids — the question is never how many lines, it is how many of them a reader would miss.
  * **The commit message is where the process goes**, not the file: what was tried, what was measured, what was ruled out, what was verified. The comment holds the *standing* reason — the part that is still true next year. Lifting a commit body above a function is how a file stops being readable, and it dates badly, because a commit describes a moment and a comment describes the code as it is.
* **Doc comments are load-bearing here.** This codebase states *why* in the comment above the thing, at length — `internal/infrastructure/announce`, `rest.PermissionRevision`, `rest.EventStream`, `service.PrincipalByID`, `noticePermissionChange` and `mutate` in `app.js`. Read the comment before changing the code: it usually already contains the reason the obvious simplification is wrong, and often the incident that produced the rule. When you change such code, the comment is part of the change.
  * **Every package opens with a package comment, and `ST1000` now says so.** This is the tree's own convention rather than an imported one: twenty-seven of thirty-eight packages already had one before anything enforced it. `.golangci.yml` re-enables the check, which golangci-lint excludes from its default set, so a package added without one is a red CI run rather than something noticed a year later. Packages made only of `_test.go` files are exempt and the check skips them itself.
  * **Where it goes is decided, not free.** There is no `doc.go` anywhere in this tree, and adding one would be a second convention rather than a tidier version of the first. The comment lives in the file named after the package where there is one — nineteen of the twenty-seven — and otherwise in the file carrying the package's subject: `directory` uses `ldap.go`, `rest` uses `errors.go`, `spreadsheet` uses `timesheets.go`, `service` uses `visibility.go`.
  * **It says what the package is *for*, which is not what it is called.** "Package command holds the write DTOs" restates the name and is exactly what the rule above deletes. What earns the space is the constraint a reader would otherwise have to rediscover: that `model` imports nothing but the standard library and why that is the architecture rather than an accident, that a partial update needs its third state said out loud, that the result types in `common` are *not* the wire format because `rest` converts them first.
  * **A doc comment can be attached to the wrong declaration and still read correctly in the file.** `TabName`'s sat above `TitleIn` with no blank line between the two blocks, so the toolchain read both as one comment belonging to `TitleIn`: `go doc` opened that method with a description of a different one and printed nothing at all for the other. Reading the file does not show this and no test did either — `go doc` on the declaration is what shows which one the toolchain thinks the block belongs to. Found by `ST1020`, which is why that check and its two siblings are now on: they compare a comment's first word against the declaration the *toolchain* attached it to, so what they really guard against is a comment that has drifted onto the wrong thing. A doc comment therefore starts with the name of what it documents — a function, a type, a variable or a constant — and that is not a style preference here, it is the only thing standing between a reader and somebody else's description.
    * **Those three checks only ever saw half the tree, and `TabName` was the half they could see.** All of `ST1020`, `ST1021` and `ST1022` are exported-only, and inside a grouped `const (...)` the group's own comment satisfies them, so the members go unexamined. Five more of exactly the `TabName` shape were sitting in the tree with a clean `golangci-lint` run over them, every one on an unexported declaration: a one-line comment for `ptr`, `read`, `dailyCap`, `projectFilter` and `Own` had each fused to the block below it, so the toolchain gave the lower declaration both and the upper one nothing. `test/doccomments_test.go` covers what the three cannot.
    * **It asks four questions, and the sharp one first.** `TestNoDocCommentOpensWithAnotherDeclarationsName` reports a comment opening with something that looks like *another* declaration's name — a compound identifier, or a word this file declares. That is the shape that hurts, and it caught all six drifted comments with no false positives.
    * **`TestADocCommentOpensWithTheNameItDocuments` then holds the rule this file states**, once the tree was brought to it: twenty-two declarations had opened with a sentence instead of a name, several of them in const blocks where the members either side did it correctly, so it was drift rather than a style. Three shapes are recognised rather than reported, because each is right: a leading article (`A Sealer encrypts…`, which `ST1021` also accepts), a spec declaring two names at once (`HeaderWidth, HeaderHeight = 440, 80`), and a comment introducing a group — recognised by the member below it having no comment of its own, which is what a group looks like and what a documented run of constants does not.
    * **The other two ask where a comment points rather than how it opens, and one of them had been in the file unnamed here.** `TestNoDocCommentIsCutLooseFromItsDeclaration` reports a top-level comment attached to nothing whose first word is a name declared in the same file — a blank line or an inserted declaration is enough, and `go doc` then prints nothing for the thing it was written for. `TestNoDocCommentNamesADirectoryAsAPackage` reports a comment qualifying an identifier with the name of a directory that declares no package: twelve of those sit under `internal/` and `cmd/`, and the word names nothing that can be imported, so the reader follows it to a package that is not there. The tree has none today, which makes it a regression guard rather than a report — and the narrow question is the only answerable one, because Go spells packages and variables alike and a qualified name in prose cannot be resolved without type information. A directory holding no Go files can never be the left half of anything.
    * **An unparenthesised declaration carries its comment on the block, not on the spec.** `var x = 1` under a doc comment reaches the AST with the spec's `Doc` nil and the block's set, and a check that reads only the spec passes over it in silence — measured, by breaking `scheduleBounds` on purpose and watching the case say nothing.
* **A file is too long once it has outgrown its own description, and length is only how that gets noticed.** Measured on this tree rather than imported from somebody else's, so that the number describes what is already here: a production Go file has a median of 138 lines and a ninetieth percentile of 449, and the browser suite writes one subject per file — all but three of its fifty-odd files are under 500 lines. **The budget is 800 lines**, which is where a file here stops being ordinary, and crossing it is a question rather than a verdict. It obliges one of three answers, and the answer is written down rather than remembered:
  * **Split it**, where the file holds several subjects that happen to share a package. This is the usual answer and Go makes it nearly free, because the methods of one type may live in several files: `SettingsHandler` was seven subjects in one file — limits, branding, timezone, the directory, the datasource, maintenance, telemetry — each carrying its own DTOs beside its own handlers, and it is a file per subject now while staying one type.
  * **Shorten it**, where the length is repetition rather than subject matter. A file that is long because the same twelve lines appear nine times is the one case where the budget is measuring the right thing directly.
  * **Keep it and say why**, where the length *is* the subject. `migrations.go` is an append-only chain and a second file would put the order in two places; `main.go` is start-up ordering, which is the one thing splitting destroys.
  * **Splitting is not automatically the improvement, and this repository carries the scar.** `infrastructure/selfupdate` was two files until they were found to hold the same body — the split is what let the two copies drift unwatched. A split that separates two subjects is worth making; one that separates a subject from itself is how a duplicate starts. So the question the budget asks is "what are the subjects in here", never "where is the halfway line".
  * **`test/filelength_test.go` is what makes this a rule instead of an intention.** It fails on a file over the budget that no row names, and on a row naming a file that is gone or has come back under the budget — so the list can neither fill up with exemptions nobody reads nor rot into a description of a tree that has moved on. Everything over the budget today is in it with its reason, the three web assets included: `app.js` has no build step to split it and is governed by the section rotation below instead, and the stylesheet and the document are one stylesheet and one document. **Where the honest reason is a split nobody has made yet, the row says exactly that** rather than inventing a justification: a list that is wrong about why a file is long is worse than the file, because it is what somebody reads instead of the file.
  * **What it caught first is what the rule is for.** `test/browser/admin_test.go` had reached 5,744 lines and seventy-seven cases across two dozen unrelated subjects — the footer, the stopwatch, the charts, the guided tour, drafts, correcting a project — while its opening sentence still said it covered "three things that can only be checked in a browser" and its section banners stopped at line 1,336. Neither had been contradicted, because nobody reads 5,744 lines: the file had stopped describing itself and no check could say so. It is twenty-five files now, one subject each and the shared helpers in one, on the convention the rest of that directory already followed.
* **Agentic Auditing Workflow:** Always document findings sequentially in an `AUDIT_REPORT.md` scratchpad.
  1. **Automated first:** Run `golangci-lint run --build-tags "browser integration firefox" ./...`, `go test -race ./...`, `go mod tidy` and `govulncheck ./...`, plus the repository's own checks from Section 3 (`deadcode`, the compose config sweep, `go test ./internal/interface/web/`). Document hard facts.
  2. **Conformance sweep — check the tree against every rule *this file* states mechanically, and put the result in the report as a table.** This is not a re-run of the linter: these are this document's rules, and nothing enforces them. Sweep for a `panic()` outside the one permitted; a SQL statement built by concatenation or `Sprintf`; `path/filepath` on an embed, URL or route path; an inline style or inline `script` in the markup; a user-facing string that does not go through `t('...')` or `data-i18n`; a package-level `var` that is mutable after startup; a `time.Sleep` on a path a request is waiting on; a stuttering `pkg.PkgThing`; a state reported with a toast instead of a banner; a project id read, totalled or changed without passing `RequireVisible`; a stored date built with anything but `model.CalendarDay`. Every hit is read before it is called a violation — the sweep produces candidates, and most of them are not:
     * `internal/interface/web/web.go:85` is the one permitted panic (the embedded assets are missing, so the binary was built wrongly).
     * `internal/infrastructure/persistence/migrations/migrations.go:1337` builds SQL with `Sprintf` and is safe: the only interpolated value is the compile-time constant `model.RoleUser`, and the comment above it says why the constant rather than a literal.
     * `announce.Announcement`, `rest.Restart`, `rest.RestartHandler` and `rest.RestartResponse` are name-prefix accidents, not stutters.
     * Three places call `Project.VisibleTo` directly instead of `RequireVisible`, and all three are right: `project_application_service.go:140` *filters* a list rather than refusing a request (and carries the `ViewerID != 0` guard itself), `workbook_application_service.go:306` has to answer with a row-level refusal rather than an `apperror` and deliberately reuses the "no such project" wording so existence is not revealed, and `timesheet_application_service.go:276` cannot reach the zero case at all because `requireUserAndProject` looks the account up first and a booking always belongs to a real one.
     * **Seven hygiene sweeps belong to the same step, and they are named separately because each one has a known answer to compare against.** A sweep whose expected result is written down is one whose *changed* result is the finding; a sweep with no expected result produces a list somebody reads once and never again. Counts below are what each returned when it was written:
       * **Context** — `context.Background()` outside start-up wiring and shutdown timeouts, `context.TODO()` anywhere, and a `context.Context` that is not the first parameter or is not called `ctx`. Seven, none and none. All seven are in `cmd/main.go` and the installer's own shutdown, which is exactly where Section 5 permits them.
       * **Logging** — `fmt.Print`, the standard library's `log`, and a write straight to `os.Stderr`, plus `console.*` in the assets. Five in Go, all in `cmd/main.go` and all where no logger can take the line: what `--version` prints, the sentence a rolled-back binary prints and the error when the rollback failed, `die` (which undoes the capture first, because the process is going), and the one line saying the log could not be captured. Those are a command's output, or the last word of a process with no logger, rather than logging, and telling the two apart is the whole of what this sweep is for. One `console.warn` in `app.js`, in `loadOperational`, is a diagnostic for a field the markup has lost, and the comment above it says why it must not throw.
       * **Error handling** — an `fmt.Errorf` carrying an error without `%w`, and a dropped `_ =`. None of the first. Of the second, all but a handful are `Close` inside a `defer`; the rest are deliberately best-effort and say so in a comment above the line, which is the standard to hold them to, because a dropped error with no sentence beside it cannot be told from a forgotten one.
       * **Orphaned translations** — already three tests rather than a grep, so the sweep is `go test ./internal/interface/web/`: `TestNoTranslationIsUnused` for the orphans and the two coverage cases for the gaps in the other direction.
       * **Orphaned constants, variables and methods** — for constants and variables this is a test rather than a sweep, `test/orphans_test.go`, because the question has one mechanical answer: a package-level value under `internal/` or `cmd/` whose name appears nowhere else in any Go file, the tagged suites and the tests included, fails unless a row says why it is kept — and a row that has stopped being needed fails too. Methods stay a sweep, the same parse widened to every declaration, because there it over-reports by construction: an interface implementation is a use nobody spells, so `MarshalJSON`, `UnmarshalJSON`, both `Unwrap`s and the four `webAuthnUser` methods come back every time and are none of them findings.
       * **Comments that restate the line beneath them** — every word of the comment already present in the next line, which is the one shape of a redundant comment a program can recognise. The rule in this section is far wider than that scan, and the rest of it is only readable.
       * **The same reason written twice** — normalise every comment block by dropping its leading identifier and collapsing the whitespace, then look for two that come out identical. This is the mechanical half of saying a thing once, at the narrowest place that owns it: a rule written out in two files is one explanation and one copy, they drift apart, and the copy is what somebody reads. **Two today**, measured over `internal/` and `cmd/` at 120 characters and up, and both are the benign shape: the sentence about what a success is called, shared by the datasource and the directory connection tests, and the reader's-zone note on two sibling handlers in the same file. So two is the expected result and a *third* is the finding.
     * **The parenthesised `const` block is this tree's recurring blind spot, and it has now hidden two different things.** It hid doc comments that had drifted onto the wrong declaration from `ST1020` and its siblings, because the group's own comment satisfies them; and it hides a dead constant from `unused`, because staticcheck treats a const group as one unit. Measured rather than inferred, by three probes: an ungrouped unused `const`, `var`, `func` and `type` are all four reported, a `var` inside a group whose sibling is used is still reported — and a `const` inside such a group is not. That is why `defaultAutoCloseAfterDays` sat in `internal/infrastructure/config` unread by anything, in a package `golangci-lint` called `0 issues`. When something turns out to be invisible here, ask whether it was in a `const` group before assuming the check is at fault.
  3. **Manual Deep Dive:** Actively read files and search for:
     * *Architecture:* run the dependency-direction grep from Section 5 and report the count, rather than reading three services and forming an impression. Zero is the current state, so a hit is a regression.
     * *Business logic:* work through **What the domain guarantees** in Section 5, rule by rule, and say for each one where it is enforced and what would happen if a caller skipped it. This is the step that is easiest to skip and hardest to fake: layering and error wrapping can both be clean while a report totals somebody else's hours.
     * *Errors:* Grep for `return err` / `fmt.Errorf` to enforce `apperror` usage and missing DE translations.
     * *State:* Grep for package-level `var` and unprotected maps (race conditions).
     * *Frontend:* Check JS/HTML for inline styles, `script-src` violations, and UI DOM quirks.
     * *Duplicates:* Search for redundant business logic or duplicated UI controls.
  4. **When a fix lands, look for the sibling.** Three of the first six sections read in the `app.js`
     rotation yielded a defect, and all three were one shape: **a rule applied in one place and missing
     in the second place that needed it.** `mutate` wrapped a write and the reload behind it in one
     `try`, while the two other callers of `refreshAll` already told those apart. `onwardView` took the
     remembered screen unchecked, while `startingView` checked the same value against the tabs and said
     in a comment why. `handBackTheScreen` reset every form on the way out, and the stopwatch's controls
     are deliberately not in a form. The same shape produced the handover flake twice over: the shared
     wait was fixed and a copy of it in one case was left behind.
     * **No scan finds these, and that is the point rather than a gap in the tooling.** Both places are
       correct read on their own; only the pair is wrong. A duplicate-block scan does not see it because
       the code is not duplicated - the *reasoning* is, and only once.
     * A fourth followed, and it was found *by asking* rather than by reading on: `formData` drops an emptied box, so a cleared description saved as no change - and the project form had already met that and worked around it for itself. `correctionFrom` is the shared reader now.
     * So the habit is the check: having fixed something, ask what else asks the same question, and
       whether the answer is written down twice. The remedy is usually one shared function - `viewIsOffered`,
       `theApplicationAnswered`, `timesheetScopeOf` - rather than a second correction.
     * **Prefer the remedy that makes the omission impossible over the one that has to be remembered.**
       A second correction fixes today's pair; a shared seam fixes the third call site nobody has
       written yet. `settleReleaseWatch` is the shape: three browser cases each had to settle the
       release check before saying what the banner should show, none of them did, and the one that
       lost the race failed on CI while passing alone. The fix was not three waits but one helper

* **A finding is fixed; a decision is asked about; a candidate that is neither is written down and dropped.** Three outcomes, and mixing them up is expensive in both directions - fixing somebody's deliberate choice unasked, or asking permission to close a hole.

  **It is a finding when somebody can be wrong because of it.** Seven shapes, each drawn from something this repository actually had:

  * *Work is lost, or refused when it should succeed* - a cleared description saved as no change, a year of days refused because the picture was three times the bound.
  * *Something outlives the thing it belonged to* - a stopwatch still painting one person's time onto a handed-back screen, a sealed page after the session under it ended, an overlay over the sign-in form.
  * *A test passes on a state the wiring cannot produce* - a case that cannot fail is a green light held over a path nobody is checking, and from the outside it is indistinguishable from coverage. This repository has had one: the browser case that "passed" against unfixed code because the test cache replayed the previous result. The scenario has to be able to tell the fix from the fault, and only damaging the code under it says which kind you have.
  * *A published security advisory in a dependency*, whether or not `govulncheck` calls it reachable.

Do not fix them unasked: a repository where an agent quietly restyles what it passes is one nobody can review.

Fixing something that turns out to have been harmless costs a diff somebody reads; leaving something that turns out to have mattered costs whoever is using the application, and they will not be filing it as a finding.

* **Iterative Audit Limits:** When asked to loop until the code is "professional", use hard metrics. `golangci-lint` at 0 warnings and a green race detector are the **floor, never the finish**. **There is no iteration cap.** A session runs until the target state below is reached, pauses only for the three stops named there, and if it can move no further first it says so and names what is left.
  * **The cap used to be three, and what replaced it is a definition rather than nothing.** Three was a guard against grinding, and it was the right guard while there was no way to tell progress from motion — an audit that could not say which way it had moved had to be stopped by counting. The four conditions below are that way, so the count is doing no work any more: a session that meets them is finished whether that took one iteration or six, and a session that does not is not finished at three. What the cap did buy, and what has to be kept without it, is that a session cannot run silently — every iteration still records the lenses it applied and what stayed unread, and every read still moves its ledger row in the commit that lands it, so a session cut short hands the next one an exact position instead of a summary.

    2. **`golangci-lint run --build-tags "browser integration firefox" ./...` reports 0 issues.**

    * **A fix that buys little.** It is a finding by the seven shapes, and either the path it sits on demonstrably cannot be reached — shown, not argued — or the change costs more than the failure it prevents: a wide diff for a narrow gain, new risk on a path that touches somebody's recorded hours, a seam that exists only for a test. Name it with both sides and ask. This is **not** a way round the doubt rule: when it is unclear whether the path is reachable or whether the failure matters, it is a finding and gets fixed.

A duplicate only a block-hash scan sees survives any number of audits that never run one. * **Idiomatic Go:** Strictly follow [Effective Go](https://go.dev/doc/effective_go) principles for all new code and refactorings. A swapped `viewerID` and `onlyUserID` is a report that answers, and answers with somebody else's hours. The second is worth spending a type on; the first is not, and treating them alike is how this becomes a rewrite.

A constructor is.** Wrapping the arguments in a struct moves the transposition into the literal, which is just as swappable — `go vet`'s `composites` check only fires for *imported* types, so a positional literal of a same-package struct is unflagged. Worse, it turns a compiler-enforced "you must pass this" into a silently defaulted zero value, and here that is not a missing argument but a decision: Section 5 says a `viewerID` of zero means authentication is switched off and sees everything. A forgotten field would widen visibility rather than fail.
    * **So ask in this order and stop at the first yes.** Do the values name a thing? Then a struct built by a constructor *whose own parameters differ in type*, so the caller cannot pass the two separately. Do they belong to something that already exists? Then a method, which is stronger than a struct and costs no new type. Is only the transposition the worry? Then a named type — `announce.Kind` is the tree's one existing example of the shape, and a `ViewerID` of its own would make the swap a compile error with no struct at all. Otherwise leave it, because a bag with no name is worse than the parameter list it replaced.

A rule that would flag several thousand existing lines is not a convention, it is a rewrite.

* **Context & Session Protection:** To prevent session limit crashes:

A document with numbers that are visibly wrong teaches whoever reads it to skim the ones that are load-bearing, and those are the ones this file is for.
  * **Read the document a line at a time when checking it mechanically.** Backticks in a file with fenced code blocks do not pair up when the whole text is scanned at once: everything after the first fence matches the wrong partner. Measured here, that returned 6 of 13 paths and reported nothing wrong, which is worse than having no check at all.
* **`test/configkeys_test.go` compares what the binary reads with what the operator is told,** in both directions: a key read through `Config.Get` that appears in none of `cmd/configs/.env`, `deploy/.env.example`, `deploy/.env.binary.example` or `deploy/OPERATIONS.md` is a knob nobody can find, and a variable an example file sets that nothing reads is a knob that does nothing — which is worse, because it is followed. Three variables are set for somebody else to read and are named in the test: `GOFR_TELEMETRY` and `SHUTDOWN_GRACE_PERIOD` belong to GoFr, `GTR_VERSION` to compose. A fourth is a decision to write down there, not a prefix to widen.

## 3. Testing & Commands

* **Task runner:** [Task](https://taskfile.dev/) via `Taskfile.yml` at the repo root; `.taskrc.yaml` holds the run settings (`interactive: true`, so a missing enum-constrained variable is prompted for rather than failing). `task --list` shows every task and `task --summary <name>` its rationale — those summaries are the authoritative explanation of why a step exists, so read one before changing that task.
* `task test` (Unit), `task test:integration` (SQLite/PG/MySQL), `task test:browser` (Chrome/chromedp), `task test:firefox` (BiDi), `task test:ldap` (a real directory), `task test:traces`, `task test:all`. `task stage` runs the shipped image against a real database, directory and collector; `task probe` checks a database or directory connection using the application's own drivers.
* **A browser counter-check needs `-count=1` when only `app.js` changed.** The assets are compiled into the *application*, which `test/harness` builds at test time; they are not an input to the browser test package, so Go's test cache sees an unchanged package and replays the previous result. Reverting the fix and re-running then reports the *fixed* outcome, which is the one way a TDD counter-check can lie in exactly the direction that matters. Caught here by a case that "passed" against unfixed code while a direct probe of the same page showed the bug; the giveaway is `ok ... (cached)` in the output. `internal/interface/web` does not have this problem - it embeds the assets, so changing one changes that package.
* **Run the task, not the tool underneath.** They wrap the same `go test`, but they are not interchangeable with it. `task test` depends on `tidy` and sets `GOTMPDIR` under the project directory, because Go writes each test binary to `%TEMP%\go-build` and real-time virus scanning on Windows intermittently locks those files — "Access is denied" on a package that compiles perfectly well. A bare `go test ./...` outside a task is fine for a quick single-package check; use `GOTMPDIR` if it starts failing for no reason.
  * **The suites also carry the parallelism CI runs them at** — `-parallel 4` for the integration suite and `-parallel 2` for the browser one. Without it `go test` uses `GOMAXPROCS`, which is 24 on this machine, and every case starts a real instance of the application and (for the browser suite) a headless Chrome to drive it. Two dozen at once does not fail cleanly: it comes back with a scatter of "the application did not become ready within 1m0s", a different scatter each run, none of it about the change being tested. A local gate that fails at random is one people stop reading — and it is not the gate, because CI measures something else.
* **The suites are separated by build tag, not by directory alone:** `integration` (three dozen files), `browser` (fifty-odd) and `firefox` (four). The only build tags under `internal/` are platform ones — `unix` / `!unix` in `infrastructure/restart` — so a scan, a linter run or a test run that only ever sees the host platform is blind to `restart_other.go`, which no suite tag covers either. `infrastructure/selfupdate` was the second such pair until its two files were found to hold the same body; they are one file now. That is the general remedy where a platform split has stopped buying anything, because the split is what let the two copies drift unwatched.
* `golangci-lint run --build-tags "browser integration firefox" ./...` — the tags are not optional. Without them the integration, browser and firefox suites are invisible to the linter, which is roughly fifteen hundred lines that decide whether a release is trustworthy. `.golangci.yml` already sets them for a bare `golangci-lint run`; the version is pinned in `.golangci-lint-version` (v2.13.1) so CI, the release workflow and a local run all mean the same thing, and so a new linter release arrives on a deliberate bump rather than in the middle of a release.
  * **`.golangci.yml` also carries an explicit staticcheck `checks` list, and it is written out because it has to be.** `checks` *replaces* golangci-lint's default rather than adding to it, and the tool offers no way to print what that default is — so switching one check on means naming the whole set. The whole staticcheck set is on there apart from `ST1003`, which judges names rather than form and is the one check whose findings would be arguments about taste. That is wider than golangci-lint's default, and it was checked before it was committed to rather than hoped for: with everything on, this tree reports nothing beyond the violations that change fixed. Measured the same way: it carried forty-nine `ST1000` violations while a plain `golangci-lint run` reported `0 issues`, which is what a default exclusion looks like from the outside.
  * **The editor is set to agree with that list, and it takes a deliberate setting to do so.** `gopls.ui.diagnostic.staticcheck` has three values rather than two — `false` disables every staticcheck analyser, `true` enables *all* of them, and leaving it out enables a subset gopls's own maintainers chose. `.vscode/settings.json` sets `true` and then switches `ST1003` back off under `gopls.ui.diagnostic.analyses`, so what is underlined while editing is what CI will refuse. A squiggle for something the gate does not check is how people learn to stop reading squiggles.
  * **`.vscode/` is committed, and that is what makes the line above true for a clone rather than for one machine.** It was ignored until the editor was brought into step with the gate, at which point ignoring it meant every clone inherited the enforcement and none of them inherited the display. What is in there is the workspace's understanding of this repository: the build tags without which gopls does not parse the three tagged suites at all, a `GOTMPDIR` outside the `%TEMP%` path real-time scanning locks, formatting switched off for the embedded assets so a stray save cannot reformat 12,500 lines of `app.js`, and debug configurations that run from `cmd/` because GoFr resolves `./configs` from the working directory.
  * **Nothing machine-specific goes in there now that it travels.** The one absolute path it had — a home directory inside the race-detector's `docker run` — is `$(pwd)` instead, because a task runs from the workspace folder and Git Bash prints it in the `/c/Users/...` form the daemon wants; `${workspaceFolder}` is the wrong tool there, since VS Code substitutes it in the Windows spelling that line exists to avoid. What remains is the Git Bash executable, which is a Windows default rather than one person's choice, and it carries a comment saying what to change elsewhere.
* **Race Detector:** `go test -race ./...` is mandatory, and it does not run on this machine: `CGO_ENABLED=0` with no gcc on the PATH, and the race detector needs cgo. **Fallback, as it actually works here:**

  ```bash
  MSYS_NO_PATHCONV=1 docker run --rm -v /c/Users/Dennis/Projects/go-time-recording:/app -w /app -e GOFLAGS=-buildvcs=false -e GOTOOLCHAIN=auto golang:1.27 go test -race ./...
  ```

  Four details, each of which was found by the command failing without them. `MSYS_NO_PATHCONV=1` stops Git Bash rewriting `-w /app` into a Windows path — without it the daemon is handed `C:/Program Files/Git/app` and refuses, which reads as a Docker problem rather than a shell one. `golang:1.27` rather than `golang:latest`, so the toolchain is the right minor. `GOFLAGS=-buildvcs=false` because the mounted `.git` belongs to another user inside the container. WSL is *not* a fallback here: the Ubuntu image on this machine has no Go installed. Around ten minutes for the whole tree, most of it the service and web packages.
  * **`GOTOOLCHAIN=auto` is the fourth, and it is what makes the third survive a patch bump.** A minor tag lags the patch releases - `golang:1.27` was still go1.27.0 on the day `go.mod` moved to 1.27.1 - and the official images set `GOTOOLCHAIN=local`, so the container does not fetch what the module asks for, it refuses: `go.mod requires go >= 1.27.1 (running go 1.27.0; GOTOOLCHAIN=local)`, and not one package is tested. `auto` lets it download the toolchain `go.mod` names, which lands in the mounted module cache and so is fetched once rather than per run. Pinning the patch in the tag instead would work today and be wrong again at the next bump; this way the command follows `go.mod` without anybody editing it.
* `go mod tidy` & `govulncheck ./...` (Mandatory dependency checks).
  * **An advisory with no fixed release is carried in a register in `ci.yml`, never suppressed and never simply endured.** Upstream sometimes has nothing to move to — GO-2026-6452 is the first here — and then the choice is a gate that is red on every pull request for weeks, which is a gate people stop reading, or a written exception. The register is the exception, and three rules keep it from becoming permanent: an advisory it does not name fails the build; an advisory it names that `govulncheck` **no longer reports** also fails, so an entry cannot outlive its reason; and each entry carries a date after which it fails on its own. Adding a row means fixing what can be fixed first — GO-2026-6452's row existed beside a guard in `rowsOf`, not instead of one.
    * **The register is empty today, and its first entry left while the guard beside it stayed — both rightly.** On 2026-09-24 the database began listing excelize v2.11.0, which `go.mod` already required, as the fix for GO-2026-6452, and that is true: the advisory is the in-memory lookup in `cell.go`. `govulncheck` stopped reporting it, and the second rule failed the build as designed. But measured, v2.11.0 still panics on the crafted workbook, because a spilled shared-string table goes through `getFromStringItem` in `rows.go` instead — a second flaw, GHSA-wcg2-648h-mhxq, fixed upstream in f98df08 after v2.11.0 and, as of 2026-09-25, in no release and no database. The two had been read as one advisory all along, and it took the first one being fixed to tell them apart. What used to be the row's job — failing once the reason is gone — is now `TestExcelizeStillPanicsOnASpilledNegativeSharedString`, which asks excelize directly and goes red once a release carries that fix. **The general lesson: an advisory marked fixed covers the flaw it describes, not your path through the same function — measure the path.**
  * **The step is written out rather than a bare invocation, and that is measured rather than fastidious:** `-format json` exits **0** whether or not it found anything, so unlike the text format nothing about govulncheck's own exit code can fail the build. The parsing is the only thing that can, which is why it checks itself first — a non-zero status, a report with no progress record, a `jq` that cannot read it, and a report carrying findings none of which can be extracted are each a failure rather than a clean scan. Same trap as the `deadcode` wrapper above, and the same remedy.
* **This repository's own checks live in `ci.yml` rather than in the Taskfile, and each exists because that class had already gone wrong here.** They belong to an audit's automated pass, not to a list of optional extras:
  * **Unreachable code** — `deadcode -test -tags "integration,browser,firefox" ./...`, and the tolerance is **zero**: there is no baseline to keep. Added after a pass found six, one of which was `OvertimeService.BalanceForAll` computing every user's balance for a team overview this application deliberately does not have. The tag list is what stops it reporting the test harness as dead. Pinned (v0.49.0), unlike govulncheck: what it reports depends on the analysis, so a new release finding something new should arrive on a deliberate bump.
    * **It prints its findings and then exits 0, so the shell around it in `ci.yml` is the check** — the output goes to a file and the step fails when that file is not empty. Verified rather than inferred from the wrapper's existence: an unreachable exported function added on purpose was reported as `unreachable func` and the command still returned 0. Simplifying that step to a bare invocation would leave a green tick over every finding, which is the one way this check can fail that nobody would see.
    * **A zero from it does not mean there is no dead code, and this is not a quibble.** `deadcode` uses rapid type analysis: as soon as a type is boxed into an interface anywhere — `json.Marshal`, a `%v`, a `t.Logf` — it must assume a type assertion elsewhere could call any of that type's methods, so it marks **every method on it** reachable. Nearly every model type here is marshalled, so a method on one is effectively invisible to that scan. Measured: three methods with no reference anywhere in the repository, tests included — `Project.BelongsToSomebody`, `Timesheet.Recorded`, `User.EffectiveMaxDaily` — sat behind a clean `deadcode` run. The last mattered: it computed a *different* daily cap from the one the service enforces, so the next caller reaching for "the user's effective maximum" would have found the superseded rule under the obvious name. The lens that finds them is a name search over method declarations, and it over-reports: six of its nine hits were interface implementations (`webauthn.User`, `json.Marshaler`), which have to be read before being called dead.
  * **Deployment compose files** — `docker compose config` over every documented overlay combination, plus a check that `compose.yaml` still *refuses* to start without `DB_PASSWORD`. Nothing in the repository had ever parsed these, so a typo in an overlay was found by whoever was deploying, at the moment they were deploying.
* **`internal/interface/web/` is the third check, and the largest:** over eighty cases asserting the *structure* of the interface against the code behind it — every route described in the OpenAPI document and every description a real route, every permission the markup names existing and checked somewhere, every gated element reachable by some seeded role, the form limits being the ones the server enforces, the charts reading the fields the statistics endpoint sends, no inline style, no inline script, no form able to fall back to GET, and no banner offering a way to dismiss it. Run `go test ./internal/interface/web/` after touching anything in the interface, not only after touching a string.
* **Definition of done, before opening a PR:** `golangci-lint run --build-tags "browser integration firefox" ./...`, `go test -race ./...`, `go test ./internal/interface/web/`, a clean `go mod tidy`, and the suite that matches the change (see *Scoping*). CI is the gate, but a check nobody ran locally is one that fails in CI on the day it matters.
* **Scoping:** Run *integration* for handler/service/migration changes. Run *browser* for UI changes.
* **Test style:** plain `testing` — there is no `testify/suite` here and testify is only an indirect dependency. Use the in-memory repositories in `internal/infrastructure/persistence/memory` and the `newFixture` helper in the service package rather than hand-rolling a mock; `test/harness` builds the real binary once per suite and starts an instance per case, which is what `test/integration` (HTTP), `test/browser` (chromedp) and `test/firefox` (BiDi) all drive. A case that measures something visual saves the picture it measured — `test/browser/*.png` is git-ignored.
* **Browser Suite Notes:** Runs parallel and is load-sensitive even at the two-at-a-time the task now pins. Under a full-suite run a case can still fail with `page load error net::ERR_ABORTED` or a download that never lands; re-run the case on its own before believing it — and if it fails alone, it is not load, so read it rather than re-running it. Fix missing waits instead of bumping timeouts, and never turn a real failure into a longer timeout.
  * **Passing alone is not evidence of noise, and reading that as noise has cost a release.** `TestAFailedConnectionSaysSoInGermanAndKeepsTheDetail` failed on `main` three times with "Die Verbindung funktioniert." where a refusal was expected, passed alone every time, and was re-run every time; the third one skipped the release for the commit carrying two security advisories. It was a real error in the case: it set the datasource type from a script, and `showRunningConnection` deliberately puts the running type back over anything not chosen by a *trusted* event, so whenever a reload landed after the typing the case tested the instance's own working connection. **A case that depends on which of two things lands first has a race in it, and the remedy is to force the order rather than to re-run until the machine picks the one you wanted** — forced, this failed in seven seconds where CI needed one run in ten.

## 4. Frontend & Pitfalls

* **Vanilla JS UI:** No build step, `go:embed`, strict CSP (`script-src 'self'`). No inline handlers/styles. Setting a style from script goes through the CSSOM (`el.style.minWidth = ...`), never through a `style` attribute.
* **Every user-facing string goes through `t('English literal')` — the English literal *is* the key.** `TRANSLATIONS.en` is deliberately empty, so a key nobody has translated still renders, in English, rather than falling through to a language the reader may not know. Markup carries its English in the element and names its key with `data-i18n`.
  * A missing translation therefore fails **silently**. After touching any string, run `go test ./internal/interface/web/`: `TestEveryTranslationCoversTheMarkup` and `TestEveryTranslationCoversTheCodeLookups` check that every key has German, `TestNoTranslationIsUnused` that none is orphaned, `TestCodeFallbacksAreEnglish` that the fallback is the source language, and `TestEveryServerErrorCodeIsTranslated` that every code the API can return has a sentence.
  * New API error codes need their German entry in the same edit. The client renders them as ``t(`err.${err.code}`, err.message)``.
  * **One word per concept, and a test says so.** `TestOneWordForAnHour` fails if any German string writes the hour unit as a bare `h` while `unit.hours` says something else, because that is two screens disagreeing about the same unit. Hold any newly agreed term to the same standard.
  * **`/api-docs` is the one page that is not translated, and that is a decision rather than a gap.** Everything on it that carries meaning comes out of `/openapi.json` — route paths, parameter and field names, and the descriptions — all English and none of it translatable from the page. Translating the seven labels around them would leave a German frame around an English page. `api-docs.html` declares `lang="en"` and means it, while `app.js` keeps the application's own `documentElement.lang` in step with the reader's choice. The i18n tests read only `/` and `/app.js`, so nothing would report a half-translated version of that page — which is why the reasoning is written at the top of `api-docs.js` rather than left to be re-derived.
  * **There are exactly two dictionaries, and the second is not a duplicate.** The installer carries its own small table (`TestTheInstallerTranslatesItsOwnRefusals`) because it runs before there is a database, so none of the application — `app.js` included — is loaded. Any *other* second copy of a key is a duplicate; two copies agreeing today is how duplicates start.
* **A state gets a banner; news gets a toast.** A toast fades after a few seconds, which is right for "Saved" and wrong for anything that goes on being true after nobody is looking — a newer release, a restart that is coming, maintenance, rights that have changed. Those are banners in `#standing-notices`, they are not dismissable, and they go down when they stop being true. Do not report a state with a toast.
* **State/Refills:** Background loads/saves must not overwrite a partially filled form or read stale server state. `beingEdited(form)` is what tells a loader to leave a half-filled form alone.
* **Duplication:** Search for existing UI controls (e.g., password reveals) before adding new ones. One question gets one control: the role is changed from the dropdown in the user's row and nowhere else, which is why the account form puts that field away while it is editing.
* **One form, two jobs.** Creating and correcting share a form, told apart by a hidden `id` input — the booking form, the role form, the account form and the project form all work this way. A form in edit mode swaps its title and its submit label and shows its `cancel editing` button; saving calls the form's own reset so the next new record is not written over the one just saved.
* **DOM Quirks:**
  * **SVG `hidden`:** SVGs lack this property. Use the attribute + `display: none`.
  * **`form.id`:** Fails if a child input is named `id`. Always use `getAttribute('id')`.
  * **`<select>`:** Has no default empty option; restoring a form defaults to the first entry unless handled. A hidden control that is still `required` cannot be submitted past and cannot be scrolled to, so the form silently does nothing — clear `required` when you hide a field.
  * **Date fields are two boxes.** `enhanceDateFields` keeps a visible text field in the reader's own convention beside the native `input[type=date]`, which stays the named element. Set one from code with `setDateField`; writing `.value` directly changes the box nobody looks at.

## 5. Backend, Architecture, Domain Rules & Concurrency

* **Layout:** `cmd/` (`main.go` and the `configs/` GoFr reads), `internal/domain/` (`model/`, `repository/` interfaces, `service/` — the domain rules, `visibility.go` among them), `internal/application/v1/` (`service/`, plus `command/`, `query/` and `common/` DTOs), `internal/infrastructure/` (`config`, `persistence/{sqldb,memory,migrations}`, `directory` for LDAP, `announce`, `selfupdate`, `imageupdate`, `restart`, `logsink`, `tlsserver`), `internal/interface/` (`api/v1/rest`, `web`, `installer`, `cli`), `internal/pkg/` (`apperror`, `security`, `document`, `spreadsheet`, `imaging`, `qrcode`, `hosting`), `test/` (`harness`, `integration`, `browser`, `firefox`, `ldap`, `probe`), `deploy/`, `build/`.
* **Clean Architecture, and here it is checkable rather than a matter of taste.** Handlers, services and repositories stay separate, and the dependency direction is one grep: `internal/domain` may import neither `internal/infrastructure` nor `internal/interface`, and `internal/application` may not import `internal/interface`. Outside `_test.go` there are currently **zero** violations of either, so a hit is a regression and not a backlog item - state that number in the audit report rather than a verdict on whether the layering "looks clean". Business logic MUST NOT leak into an HTTP handler: the handler resolves who is calling, parses the request, and hands both to a service.
* **What the domain guarantees, and what a business-logic audit checks against.** These rules *are* the product. They are enforced in `internal/domain`, every one of them was written after the version without it went wrong, and a change that quietly widens one is the most expensive change this repository can take. An audit that only checks layering and error wrapping has not audited the business logic at all.
  * **There are no teams and no view across accounts.** A project belongs to exactly one person (`Project.OwnerID`, and `VisibleTo` is ownership); two people working on the same thing have a project each, with the same name if they like, and nothing adds them together. This is why `OvertimeService.BalanceForAll` was dead code rather than a missing feature - and why a request that would total somebody else's hours is a defect, not an enhancement.
  * **A project the viewer may not see is *not found*, never *refused*.** `service.RequireVisible` answers 404 on purpose: the difference between 403 and 404 is itself the leak. A `viewerID` of zero means authentication is switched off - the local trial case - and sees everything.
  * **Every project id that arrives from a caller passes `RequireVisible` before anything is read, totalled or changed.** The project *record* was hidden long before the hours booked against it were: opening a report was enough to learn what somebody had recorded against their own private category, and how much. Archive, transfer and both report paths each carry the check separately; the two evaluations of somebody's *own* time - the report and the statistics beside it - share one, `ProjectScope.RequireVisible`, because the statistics once let a foreign project through on the reasoning that the total could only ever be the caller's. The rule is about the id, not about what the total would contain.
  * **Two ids, two questions, and both are needed.** `viewerID` decides whether the project may be seen; `onlyUserID` decides whether other people's hours may be. `GenerateProjectTimeReport` takes both because the version that conflated them totalled every colleague's hours for anybody who could open the project.
  * **Only an `active` project accepts bookings, and only a `completed` one can be archived.** Both refusals are typed codes (`projectClosedForBooking`, `archiveNeedsCompleted`), not messages.
  * **The built-in administrator must keep a role that can still administer** (`PermRoleWrite`), or an installation locks itself out of its own user management.
  * **A stored date is midnight UTC of a calendar day and carries no zone** (`model.CalendarDay`). *Which* day is read in the user's own zone, and for the stopwatch it is the day the clock was **started** - somebody who starts at half past eleven at night and stops after midnight worked that evening. One shape only: the version that kept the zone stored 15 July as midnight in Berlin from the clock and midnight UTC from the form, overtime grouped those as two days, each was measured against a full day's target, and the balance on screen was eight hours short of the truth.
  * **One person, one running clock.** `RunningTimer` is keyed on the user, because two would pose a question with no answer - which one the next stop belongs to. It is deliberately not a `Timesheet` with a zero duration: a clock has no duration, and no calendar day, until it is stopped.
  * **A booking is at least `MinBookableHours` (0.01) and at most the configured daily cap, itself bounded by `HoursPerDay`.** Nothing rounds to a quarter-hour grid - the floor exists only to tell a short booking from a mistyped one. The same floor is published in the OpenAPI document and set on the form, so all three agree about what the API takes; changing one means changing three.
  * **A time entry has no status and no approval path.** There is nobody to approve: everyone keeps their own hours and the built-in administrator runs the installation rather than reviewing other people's work. Do not reintroduce a review step, and do not read its absence as an oversight.
  * **An empty synchronisation schedule means "do not run", and that is the safe default** - a run deletes the accounts the directory no longer holds, together with the hours recorded against them. `ValidSchedule` refuses an expression the scheduler would silently drop, because a mistyped one saves cleanly and then never runs, and a job that never runs looks exactly like a directory that has not changed. `LDAPSyncMaxDeleteRatio` bounds how much one run may remove.
* **Dependency Injection:** Inject all external dependencies (DBs, APIs) via constructors/structs to ensure code remains testable.
* **Context Propagation:** Always pass `context.Context` as the very first parameter to all functions handling business logic, DB queries, and external calls. Respect context cancellations. `context.Background()` appears only in startup wiring and in shutdown timeouts — never on a request path.
* **Goroutine Safety:** Never spawn raw goroutines without managing their lifecycle. The inventory in production code is **nine, and enumerable**: two draining the captured stdout/stderr pipes in `logsink` plus one waiting on them, two in `tlsserver` serving HTTPS and the HTTP redirect, one in the installer serving until an answer arrives, one in `restart_handler.go` waiting out the restart grace so the response reaches the browser first, one in `update_handler.go` waiting for the image updater's answer so that an update which replaced nothing does not stay announced as a restart - it ends at the answer, or after ten minutes of silence - and one in `main.go` listening for the same signals GoFr handles — a second listener on purpose, so the announcement hub is closed before the server tries to drain a stream that by design never finishes. Each of them ends with something. Do not add one outside that pattern; `golang.org/x/sync/errgroup` is not a dependency here and none of the nine needs one, so reaching for it is a dependency decision rather than a style choice.
  * **Re-count them with `ast.GoStmt` over the non-test tree, never with a grep, and that is measured rather than fussy.** `grep 'go func'` returns **eight** of the nine, because `update_handler.go`'s is `go h.awaitTheImage(c.Logger, version)` — a named method rather than a function literal. The one the grep cannot see is the one with the ten-minute bound, which is precisely the one a re-count most needs to find, and the failure is silent in the flattering direction: somebody checking the number reads eight, finds the document says nine, and concludes a goroutine was removed. A count this file calls exact is worth exactly what the command that re-checks it is worth.
* **Never `time.Sleep` where a request is waiting.** There is exactly one in `internal/` and `cmd/` — `restart_handler.go:431`, inside that detached goroutine. Anything on a request path waits on `ctx.Done()` or a ticker instead, so an abort is not invisible for the length of the sleep.
* **Shared state:** every package-level `var` in production code is an interface assertion (`var _ repository.UserRepository = ...`), a sentinel error, or a read-only table built once. Nothing mutable lives there, and that is the only reason it needs no lock. Anything that must change at run time carries its own synchronisation instead — the announcement hub is the example.
* **Database Resource Management:** the pool is **GoFr's, not this code's**. Nothing here holds a `*sql.DB` to tune, and `SetMaxOpenConns` and friends appear nowhere in the tree. Tuning is configuration — `DB_MAX_IDLE_CONNECTION` and `DB_MAX_OPEN_CONNECTION` in `cmd/configs/.env` and `deploy/.env.binary.example`, commented out at GoFr's defaults. Change those with a measured reason; do not reach for the Go API instead.
* **`./configs` is resolved from the process working directory, not from the binary.** That is GoFr's own `configLocation`, mirrored by this package's constant of the same name so `DatasourceFromEnvironment` looks exactly where GoFr will. Launching `./bin/app` from the repository root therefore finds no configuration and leaves `container.SQL` a **typed** nil, which `db == nil` does not catch; `cmd/main.go` fails fast on that rather than serving 500s. `APP_ENV` is likewise read from the environment at start-up, so setting it for a `go build` compiles in nothing and GoFr quietly falls back to `.local.env`. Both are invisible to unit tests and to running the binary from a directory that happens to contain `configs/` — verify with the actual launcher command.
* **Path handling:** `path/filepath` is strictly for real files on disk (`selfupdate`, `imageupdate`, `config`). Embedded-asset paths, URL paths and route prefixes are slash paths and must never touch `filepath` — on Windows it would build `assets\app.js`, which the `embed.FS` does not contain. The slash-only `path` package is currently imported nowhere; `fs.Sub` and `http.FS` handle it.
* **Errors:** API uses closed catalogue (`internal/pkg/apperror`), rendered client-side via `t('err.' + code)`. **Mandatory:** New codes require a German translation in tests. Never silently drop errors; always wrap them (`%w`) for context.
  * **No Panics:** Never use `panic()` for business logic, control flow, or validation errors. Return wrapped errors up the stack. `panic` is reserved for a programmer error that cannot be recovered from, and there is exactly one in production code — `internal/interface/web/web.go:85`, where the embedded assets are missing, which means the binary was built wrongly.
    * **`Must…` is a panic with a different spelling, and what decides whether it is permitted is where it sits.** There are three in production code and the word `panic(` appears in none of them, so a sweep for the word reports one site and there are four. `regexp.MustCompile` at `internal/application/v1/service/service.go:20` is at package level, which is the idiomatic use: a bad pattern fails on the very first run, deterministically, before anything is served. The two `netip.MustParsePrefix` calls in `loopback()` — `internal/interface/api/v1/rest/security.go:141` — sit **inside a function body**, which is ordinarily a runtime panic on whatever was handed in; they are permitted because both arguments are compile-time literals, so nothing a request carries can reach them. A `Must…` in a function body taking anything a caller can influence is a panic on a request path, and is refused for the same reason `panic()` is.
    * **There is also exactly one `recover()`, in `spreadsheet.rowsOf`, and it is not a licence for a second.** It exists because that is the single place where bytes somebody uploaded decide what a *dependency* does with an index, and the dependency has been wrong about that: a cell naming a negative shared string panics excelize on every release so far — GO-2026-6452 on the in-memory lookup up to v2.10.1, and GHSA-wcg2-648h-mhxq on the spilled one, v2.11.0 included (see the register above). GoFr recovers a panic raised inside a handler, so the process was never at risk; what the guard buys is the person being told their file cannot be read instead of the request dying as a stack trace. The shape of the exception is what to read before writing another one — it wraps a parse of untrusted input at the narrowest function that owns it, it sets both named returns so a recovered panic cannot arrive as an empty success, and it is registered before the resource is opened so it covers the open too. A `recover()` anywhere else is hiding a bug in this repository's own code, which is what the rule above is about.
* **Partial updates say three things, not two.** An update DTO of pointers can express "leave it alone" and "set it to this" and nothing else, so a field that has to be *emptiable* needs the third state said out loud — `UpdateProjectCommand.ClearEndDate`, and an end date that arrives present but empty. Never overload nil to mean "clear": the callers that say nothing rely on nil meaning nothing.
* **GoFr:** Config read in `gofr.New()`. Changing metrics/trace/DB configs requires storing state and triggering a restart. Anything needing the raw `http.ResponseWriter` — a connection held open and written to over minutes, like the event stream — is middleware rather than a GoFr handler, because "return a value, return an error" is the wrong shape for it by construction.

## 6. Releases

* **Two ways in, and they mean different things.** A merge to `main` cuts the next **patch**: the version is written down nowhere, the workflow reads the newest tag and counts on, so there is no file to forget to bump and no way for a tag and a constant to disagree. A tag pushed by hand (`task release VERSION=vX.Y.Z`) releases exactly that version, and the next merge counts on from it — that is how a minor or major bump is made.
* **Both paths require a green CI run on `main` for the commit being released, and neither verifies for itself.** A tag *asks* whether CI passed for the commit it points at and refuses if it has not. It used to run a subset of its own instead, which is how v0.2.0 shipped from a commit whose Firefox job was red.
* **Build from a clean tree.** The version comes from git at build time, so a dirty working tree is what the binary reports to whoever installed it.
* **Artifacts:** Builds `linux/amd64`, `linux/arm64` images, and 4 platform binaries. Images are verified on both architectures before publishing.
* **The `.syso` filename is load-bearing.** The Go toolchain links *any* `.syso` in a package directory with no import and no build tag, so `goversioninfo`'s default `resource.syso` would end up in the linux and darwin binaries too — the release builds four platforms in one loop, in one working directory. `build/windows-resource.sh` writes `cmd/resource_windows_amd64.syso` instead, where the suffix confines it exactly as it confines a `.go` file, and removes it again afterwards. `*.syso` is git-ignored for the same reason: a committed one would be linked with whatever version it was written with, for ever.
* **A version Windows cannot parse fails quietly, not loudly.** The resource script strips the `v`, takes the three numbers and zeroes the fourth, and falls back to `0.0.0.0` for a version that is not numeric at all — because an unparsed one simply reads `0.0.0.0` in the Properties dialog and says nothing about why.

## 7. Enterprise SDLC & Production Readiness

* **Zero-Downtime Migrations:** Database schema changes MUST be backward compatible. Use multi-phase deployments (e.g., add column -> dual write -> switch read -> drop column). Never drop or rename columns in a single release.
* **A migration runs against somebody's recorded hours, and it runs on three dialects.** `migrations.go` is the longest file in the repository and the chain is append-only: a migration in the middle of it can be looking at a name a later one renames, which is why the ones that need to say so do. Add to the end, never edit an applied one, and prove it under `task test:integration DB=postgres` and `DB=mysql` as well as SQLite.
  * **A migration is atomic, except on MySQL when it changes both the schema and the data.** GoFr runs each one inside a transaction — `migration.Datasource.SQL` *is* the `*sql.Tx`, so every statement in a migration commits or rolls back together, `giveEveryProjectAnOwner`'s row-at-a-time work included. MySQL commits implicitly on DDL, so a migration that alters a table and then updates rows runs its `UPDATE` outside that transaction: the schema change has landed, the data change fails, and nothing goes back. `rememberWhenASessionWasLastUsed` is what that costs — it adds `last_seen_at` and fills it precisely so an update does not sign everybody out, and split on MySQL it is the thing that signs everybody out. **A new migration needing both is two migrations, schema first.** Six existing ones mix them and are named in `TestNoNewMigrationMixesSchemaAndDataChanges`, which guards the seventh; they are listed rather than fixed because the chain is append-only and they have already run everywhere.
* **Secret Management:** Strictly forbid hardcoded secrets, API keys, or private credentials in code or configs. Use environment variables or secret stores exclusively. `configs/datasource.json` and `deploy/.env` hold real passwords and are git-ignored; the `.example` files beside them are what belongs in the repository. `deploy/.env.ci` is git-ignored too, for a less obvious reason: it holds *invented* passwords, and a file of plausible-looking credentials in a deployment folder is one somebody eventually copies.
* **The payload is personal data, and one function is the erasure path.** Recorded hours are what somebody is paid for, so an account and its record go together. `sqldb.PurgeUser` removes them in one transaction, in foreign-key order: running timers, time entries, privately owned projects, api tokens, passkeys, sessions, then the account. Directory synchronisation calls it, and so does an administrator deleting an account; it is irreversible either way.
  * **A new table with a foreign key to `users` is added to that list in the same commit.** A missing one does not fail loudly: on PostgreSQL and MySQL it makes the final delete impossible, and on SQLite - where foreign keys are not enforced unless asked for - it silently leaves rows pointing at an account that no longer exists. This has already happened once, with passkeys.
  * **`grep 'REFERENCES users(id)'` finds most of them and is not sufficient.** `projects.owner_id` was added by an `ALTER` and appears in no `CREATE TABLE`, so it is invisible to that scan - which is the general lesson: read the migration chain for the column, not only the create statement.
  * **`TestEveryTableReferencingAnAccountIsPurgedWithIt` now checks it**, in `test/purge_test.go`. It reads the whole chain for both shapes, follows `ALTER TABLE … RENAME TO` (the SQLite rebuild creates `timesheets_new` and renames it), and requires a matching `DELETE FROM` in `purge.go`. The rule above is still the rule; this is what notices when somebody does not follow it. Verified by removing each of the six deletions in turn and by adding a table with a foreign key to `users` and no deletion — every one is reported.
  * **It is a transaction and must stay one.** The reasoning that every step is idempotent and a failed purge repeats on the next run does not survive the failure it was meant to cover: the final delete is the one that gets refused, and by then the hours are already gone. Inside a transaction, the account and its hours both survive the error.
* **`deploy/OPERATIONS.md` is the operational contract** - what is being deployed, the four supported shapes (compose, compose with TLS, single binary, bare container), where configuration comes from, and which values are worth setting deliberately. It is written for whoever runs this rather than for whoever builds it, so a change to how the binary is configured, started or shut down belongs in it in the same commit. The README links it; this file is the reminder that it is part of the change.
* **Observability & Logging:** Use structured logging (e.g., standard library `slog` or project logger) with contextual keys (request_id, user_id). Avoid raw `fmt.Println` in production code. GoFr provides two health endpoints and the load-bearing one is **`/.well-known/alive`**, not `/.well-known/health`: `alive` is what the Dockerfile's `HEALTHCHECK` and `deploy/compose.yaml` both probe, so a middleware that turns it away gets the container killed and replaced. Keep both reachable. Two already depend on this and both are correct — `maintenanceExempt` passes anything outside `/api/`, and `KeepThePlainPortLocal` lets them through because both probes dial `127.0.0.1`, which is loopback.
* **API Backward Compatibility:** Do not introduce breaking changes to existing API request/response contracts without a versioning strategy. Payload fields must be treated as immutable once public. A field a browser already reads is part of that contract even when no external client exists.
  * **The contract is with installations that already exist, not only with callers, so an environment variable name is part of it too.** Somebody's `.env` on a server is the deployed half of this repository: renaming a key does not fail loudly, it falls back to the default and the setting they chose stops applying — quietly, and at the next restart rather than at the moment of the change. Rename one only with the old name still read and a release's notice, the same way a payload field would be treated. `test/configkeys_test.go` is what notices a key that has left the code while an example file still sets it.
* **What arrives is not what it becomes: bound the decoded size, not only the bytes.** One audit found this three times in three packages, and it is invisible to the linter, the race detector and every suite — there is nothing wrong with the line, and any test fast enough to keep uses an input small enough to hide it. Measured, not estimated: a 32 MB workbook unpacks to ~13 GB (deflate reaches **408:1** on real sheet XML); a 199 KB logo decodes to **244 MB** (a flat PNG compresses ~1250:1), three times per save; a 260 KB chart costs **782 MB** (a canvas produces RGBA, and splitting the alpha means inflating it all). Read the header first — `image.DecodeConfig`, or the library's own size option — refuse what is too large, and pick the bound from a measurement rather than a guess. `TestEveryDecoderOfCompressedInputIsBounded` lists every call site that decodes compressed input and fails on a new one, so the fourth is caught rather than found.
* **Input validation & injection boundaries** — validate and sanitize at the application boundary, and know which boundary each one is:
  * **SQL:** parameterised queries only, through the repository interfaces. Never build a statement by concatenation or `Sprintf` — Section 2 names the one documented exception and why it is one.
  * **HTML:** the served document is assembled server-side so it can carry the instance's own name and mark, which makes a configured title an injection site — `TestAConfiguredTitleCannotCloseItsOwnTag` is that check. A configured logo is served from an endpoint at a stable address rather than inlined as a `data:` URI, and one that is not an image is refused.
  * **Imports:** a spreadsheet row that fails says which row and why, in German as well as English (`TestEveryImportRowProblemIsTranslated`).
  * **CSRF:** a state-changing request must carry the double-submit token — the `gtr_csrf` cookie echoed back in `X-CSRF-Token` (`rest/csrf.go`). A new mutating route is inside that check, not beside it.
  * **Transport:** HTTPS is terminated in-process when configured (`tlsserver`), and GoFr's plain port then answers only the loopback address the front end dials from.
* **Authorisation is enforced server-side and only *reflected* on screen.** Every request resolves who is calling from the database, so a withdrawn right is refused on the very next call whatever the browser believes. What the interface adds is telling somebody: the revision travels on every response, the open event stream carries a change to a page nobody is touching, and the once-a-minute poll is the fallback under both. Never hide a control instead of enforcing a rule, and never offer one the server would refuse.
* **The installer's token is the sign-in.** Answering the installer proves more than a password does — it is read from the process log, and it decides where the data lives — so the browser that answered it is handed a session rather than being sent to type `changeme123`. Two conditions carry that, and both must survive any change to it: an installation that never served an installer has no token and the claim then has no working path at all (an empty configured token must be refused *before* any comparison, or an absent header matches it), and the claim stops working the moment the built-in administrator's password is changed — the same moment the documented password stops working.
* **Design rationale lives in the code and in the commit, not in an `adr/` directory** — there isn't one, and adding a parallel format would split the record. The convention is a package or declaration doc comment stating why the non-obvious choice was made, plus a commit body recording the alternatives and what was verified. Follow that for structural changes.

## 8. Agent Triggers (Prompt Cheatsheet)

**STRICT SESSION RULE (CRITICAL):** NEVER spawn sub-agents, parallel instances or background tasks. Process ONE file or logical step at a time, strictly in the main thread. Flush findings to `AUDIT_REPORT.md` as they are made.

**Run to the finish rather than stopping at every file.** A session works through the findings, commits each one atomically, merges on a green CI run and carries on; it halts only for the three stops *Iterative Audit Limits* names — a decision, a fix that buys little, a genuinely critical decision — and it runs until the target state defined there is reached rather than until an iteration count is used up. Sequential still means sequential: one file or logical step at a time, in this thread, never in parallel.

* **The Full-Spectrum Audit & Fix Loop (All-in-One Master):**
  `"Execute a full-spectrum iterative Code Audit and Refactoring cycle based strictly on CLAUDE.md. Create a feature branch first. Actively analyze, refactor, and fix all of the following sequentially with TDD and atomic commits: (1) Duplicated logic and duplicated UI controls, (2) Dead/legacy code and orphaned translations, (3) Misplaced business logic (move it out of handlers and out of app.js into services), (4) Missing German translations and untranslated error codes, and (5) Performance bottlenecks, redundant allocations, and goroutine lifetimes. Do NOT spawn sub-agents - one file at a time in the main thread. No iteration cap: run to the finish and halt only for the three stops 'Iterative Audit Limits' names - a decision, a fix that buys little, a critical decision - until the target state it defines is reached."`

* **The Deep Audit (Analysis Only):**
  `"Run a comprehensive Code Audit strictly following the Agentic Auditing Workflow in CLAUDE.md. Create a feature branch first, use the AUDIT_REPORT.md scratchpad, run the automated checks (golangci-lint with the build tags, go test -race, go mod tidy, govulncheck, deadcode with all three tags, go test ./internal/interface/web/), then the conformance sweep as a table, then the manual deep dive sequentially. Finish by recording the verdict and the invariants checked in AUDIT_REPORT.md, and by moving the ledger row in CLAUDE.md §2 on - the date, the question and the verdict - in the same commit as the fix. The report is git-ignored, so a position recorded only there is lost at the next clone. Strictly this thread; no background tasks."`
